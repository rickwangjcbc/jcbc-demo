# Issue #13 お問い合わせの対応状況別件数サマリー設計

## 要件確認書

### 目的・解決したい問題
- お問い合わせ一覧を読む前に、保存済み全お問い合わせの件数と対応状況の内訳を把握できるようにする。
- 対象は `rickwangjcbc/jcbc-demo` の Issue #13「お問い合わせの対応状況別件数サマリー」とする。
- Issue URL：https://github.com/rickwangjcbc/jcbc-demo/issues/13

### 成功基準・完了の判断
- 一覧上部に「対応状況サマリー」と「全件・未対応・対応中・完了」の件数を表示する。
- 全件数は保存済みお問い合わせ数および3状況の件数の合計と一致する。
- 新規登録・対応状況変更の保存成功直後に件数が更新され、保存失敗時には直前の件数を維持する。
- 検索・絞り込み中も保存済み全お問い合わせを集計する。
- 保存済みデータが0件なら全項目を0件として表示する。読み込み不能時にはサマリーを非表示にし、既存エラーを表示する。
- 単体テスト・E2Eと既存機能の回帰確認で上記を検証する。
- 本工程は設計資料の作成と保存後の人間による承認までとし、設計とIssueの整合確認後にのみTodoへ進める。

### 制約
- 合成データ専用の既存ブラウザアプリを対象にする。
- 保存形式・保存キー・データ読み込みと保存の契約を変更しない。依存追加、データ移行、無関係なリファクタは行わない。
- 検索・対応状況／優先度の絞り込み・並び順・登録日時・メモ・未保存メモ入力を維持する。
- 本工程ではコード実装・commit・push・PR作成・委任を行わない。
- 設計書はリポジトリルートの `specs/` に新規保存し、保存前の完了確認と保存後の設計承認を区別する。

### 内容の個別仕様
- 「お問い合わせ一覧」の見出し直下、検索欄より上にサマリーを配置する。既存の全件表示は維持する。
- 表示順は「全件」「未対応」「対応中」「完了」。各項目を「全件：12件」の形式で表示する。
- 表示専用とし、クリック操作や状態変更を追加しない。
- 件数は検索・絞り込み・並べ替え前の保存済み全お問い合わせから描画時に算出する。件数自体を別の状態やlocalStorageに保存しない。

### エッジケース・暗黙の前提
- 保存済み空配列は正常な0件とし、サマリーを表示する。検索結果0件でも全体集計を維持する。
- 保存データの読み込み失敗・不正データではサマリーを非表示にし、既存の読み込みエラーと操作停止を維持する。
- 初回サンプル投入または既存の登録日時補完の保存に失敗した場合も、読み込み完了とは扱わずサマリーを非表示にする。既存の補完保存エラーを維持する。
- 読み込み成功後の保存失敗では、直前の集計結果を表示したままとする。エラーの有無だけでサマリーを隠さない。
- 初回サンプル保存成功時は全件3件、各状況1件とする。

### 対象外
- サマリーのクリックによる絞り込み。
- グラフ・割合・優先度別など対応状況以外の集計。
- 件数の永続化、他タブとの同期・競合解決、既存データ形式の変更。

### 2. 既存実装と採用方針
- `src/inquiries.ts` の `loadInquiries` は保存済みデータの状況を「未対応・対応中・完了」に限定して検証する。サマリー側に不正データの補完や新たなエラー処理を追加しない。
- `src/main.ts` の `inquiries` は、初期読み込みと必要な初期保存の成功後に設定される。以降は `save(next)` がlocalStorageへの書き込みに成功した場合だけ更新する。
- `render()` は登録・対応状況／優先度変更・メモ保存の成功後、および検索・絞り込み・並び順変更時に呼ばれる。
- この既存契約を利用し、全件集計を描画時に再計算する。操作別の増減管理は更新漏れのリスクがあり、件数の別保存は二重管理になるため採用しない。

### 3. 集計とデータフロー
- `src/inquiries.ts` に名前付きexportの純粋関数 `summarizeInquiries(inquiries: readonly Inquiry[])` を追加する。
- 返却値は `{total: number, pending: number, inProgress: number, completed: number}` とする。空配列ではすべて0。
- `total` は入力配列の長さとし、各要素の `status` に対応する件数を数える。入力配列・要素・順序は変更しない。
- 入力は既存経路で検証済みの `Inquiry[]` に限定する。`Inquiry.status` の型変更、共通状態管理層の追加は行わない。
- `render()` 内で絞り込み前の `inquiries` を集計し、4項目のテキストを更新する。表示リストには従来どおり `filterInquiries` と `sortInquiries` を適用する。
- 全件を走査する時間計算量はO(n)、集計の追加領域はO(1)。キャッシュや差分カウンターは追加しない。

### 4. 画面構成と表示条件
- `index.html` の一覧セクション内、`list-heading` の直後に `id="status-summary"` の領域を追加し、初期状態で `hidden` を付ける。
- 領域は `aria-labelledby="status-summary-heading"` で見出しと関連付ける。見出しはh3の「対応状況サマリー」、4項目はリストとして表示する。
- 各項目は `summary-total`、`summary-pending`、`summary-in-progress`、`summary-completed` のIDで更新できる要素とし、`textContent` に「項目名：N件」を設定する。
- 操作要素やクリックハンドラー、追加のライブ通知は不要。既存の保存成功通知を利用する。
- `src/main.ts` の描画時に既存の `available` に基づいて表示する。読み込み失敗で描画されない場合も初期のhiddenが残るため、0件と誤表示しない。
- 登録日時補完保存失敗では `available` がfalseのままなので非表示を維持する。
- 保存失敗や入力エラー後も `available` はtrueのままなので、サマリーと直前の件数を維持する。
- 既存 `#count` は変更しない。既存CSSを利用できる構成とし、CSS変更は予定しない。

### 5. 操作・失敗時の振る舞い

| 場面 | サマリー | 既存状態・保存 |
| --- | --- | --- |
| 初回サンプル保存成功 | 全件3件、各状況1件を表示 | 既存の初期保存処理を利用 |
| 正常な保存済みデータの読み込み | 全件と各状況を表示 | データ形式の変更なし |
| 保存済み空配列 | 4項目すべて0件を表示 | サンプル再投入なし |
| 検索・状況／優先度絞り込み・並び順変更 | 全体集計を維持 | 件数のための保存なし |
| 新規登録の保存成功 | 全件・未対応が各1増加 | 既存の保存成功後描画を利用 |
| 対応状況変更の保存成功 | 変更前を1減、変更後を1増。全件は不変 | 同じ状況なら件数不変 |
| メモ・優先度保存成功 | 状況別件数は不変 | 既存描画・未保存メモ管理を維持 |
| 新規登録・編集の保存失敗 | 直前の表示・件数を維持 | 既存エラー、入力保持、状況選択の復元を維持 |
| JSON破損・不正データ・getItem失敗 | 非表示 | 既存読み込みエラー、操作停止、上書き防止 |
| 初回投入・登録日時補完の保存失敗 | 非表示 | 既存の補完保存エラー、操作停止、元データ保護 |
