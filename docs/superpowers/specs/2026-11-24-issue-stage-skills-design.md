# Issue作成・設計を短い入力で始めるための入口スキル設計

## 目的と範囲

`prompt-examples.md` の長文を貼り付けず、要望またはIssue番号だけで工程を指定できるようにする。初回の対象は `prepare-issue` と `design-issue` の2つ。開発・初回PR、レビュー対応、マージ確認の入口、および `double-check-loop` のリポジトリ移行は対象外とする。

## 入口と手順の正本

| スキル | 最小入力 | 適用するリポジトリ内手順書 |
| --- | --- | --- |
| `prepare-issue` | 新しい要望の一文 | `docs/ai-development/workflows/issue-creation.md` |
| `design-issue` | 単一のIssue番号またはURL | `docs/ai-development/workflows/issue-specification.md` |

実装時は、それぞれ `docs/ai-development/skills/<スキル名>/SKILL.md` に置く。入口には入力、参照先、開始と停止の条件だけを定義し、手順本文は複製しない。JAC Harnessの登録済みWorkflowを呼ばず、リポジトリのMarkdownを手順書として適用する。既存の `prompt-examples.md` は参照用に残す。新規スクリプトやIssueごとのJSONは不要とする。

## 共通の開始条件

- `jcbc-demo-agent` の `repository`、`readme_path`、`rules_path`、`project_settings_path` を使う。通常は入力し直さない。採用資料のコミットは人間が一度確定し、同じ会話では再利用する。別の会話では確認済みの記録を参照し、分からない場合だけ確認する。
- 採用コミットの `AGENTS.md`、共通3資料、対象の手順書を読み、設定値・参照SHA・対象を照合する。ローカル作業場所はGitで確認し、`origin` と案件設定が異なる場合は止める。未設定、資料の取得不能、対象の不一致、上位の制約との衝突があれば、別版や別の対象で代用せず、副作用の前に止める。
- スキルの閲覧やコマンドの引用だけでは工程を開始しない。工程への明示依頼は、Issue作成への同意や設計承認の代わりにしない。

## 工程別の動き

### Issue作成の準備

`/skill:prepare-issue 優先度の高いお問い合わせだけを表示したい` を実行例とする。対象と手順を確認した後、本人による `/skill:interview-to-issue` の明示起動を待つ。同じ会話で要望が一意なら、再入力を求めない。入口スキルは `interview-to-issue` を自動起動せず、Issueも作成しない。

作成工程では、要件の決定事項への合意と、最終Issue案全体（タイトル・本文・ラベル）への明示同意を分ける。案を修正した場合は再提示・再同意が必要。作成後は本文・URL・`Spec` を確認し、設計には自動で進まない。`Spec` がない場合の例外や作成結果不明時の対応は手順書に従い、無断のラベル作成・重複作成は行わない。

### Issueの設計

`/skill:design-issue #42` を実行例とする。番号は案件設定のリポジトリに対して解決し、作業場所と対象Issueを照合する。新規設計は `Spec`、`Design` からは未完了事項を照合した明示再開に限る。不足情報はIssue・設定から確認し、業務判断や不足する必須事項だけを人間に尋ねる。

通常・高リスク案件で必要な `expert-mode-ja` と `clarify-spec` の条件を維持する。設計資料の保存だけでは `Todo` に変更しない。人間が採用版を承認し、整合と適用ゲートを確認できた場合のみ `Todo` に変更して再取得する。軽微経路でもIssue内簡易設計への人間の承認は省略しない。実装には自動で進まない。

## 初回の受け入れ確認

| 確認すること | 合格条件 |
| --- | --- |
| 読み込みと起動 | `SKILL.md` のパス指定と実際の `/skill:` 入力を別々に試す。コマンドでは意図した定義と引数が使われ、同名の別定義や登録Workflowに切り替わらない。未検出ならコマンド対応とは報告しない。 |
| 入力の短縮 | 対象と採用版が確認済みなら、要望またはIssue番号だけで入口を使える。長文・URL・JSONの転記を要求しない。 |
| 停止条件 | 採用版や設定・資料が不足する場合、`origin` と対象が異なる場合に、Issue作成やラベル変更より前に止まる。 |
| 手動起動とIssue作成の同意 | 入口の起動だけ、あるいは要件合意だけではIssueを書き込まない。最終案全体への明示同意まで作成せず、作成後も設計を始めない。 |
| 設計の承認 | 承認前・別版への承認・重要事項が未解決の場合は `Todo` に変更せず、条件を満たす承認後に限り変更結果を再取得する。 |

パス指定で読めることと、JAC Harness上でコマンドが使えることは別に記録する。試行でGitHubへの書き込みが必要な場合は、対象と操作を別途明示し、承認を得る。
