# Demoエージェント：Issueからマージ確認までの社内利用ガイド

> 共有版：リポジトリ内の手順・説明資料です。入口は`docs/ai-development/README.md`、共通ルールは`docs/ai-development/rules.md`、案件別条件は`docs/ai-development/project-settings.md`を参照してください。本文中のパスは明記のない限りリポジトリルート基準です。アプリ登録や権限付与を行うファイルではありません。


## 1. 目的と現在の準備状況

初めて使う方向けに、`rickwangjcbc/jcbc-demo` の要件確認、設計、開発、PRレビュー、人間によるマージ後の確認を説明します。Issueを作業範囲・受け入れ条件の基準とし、承認済み設計書で詳細を補足します。

**これは運用定義の説明資料です。保存しただけで設定・実行・権限付与が完了するわけではありません。**

以下の「設計書」「保存後の設計承認」「採用版」は通常案件の表記です。第16節の軽微経路では「Issue内簡易設計」「記載後の人間承認」「承認対象のIssue本文」に読み替えます。高リスク案件には確定した追加ゲートも適用します。

- この資料更新では新規GitHubラベル `Spec`・`Design`・`Review`・`Rework`・`MergeReady` の作成や、既存4種を含む説明更新をしていません。現時点のGitHub設定も再取得していないため、整備済みとは扱いません。
- リポジトリ内のWorkflowは共有手順書です。アプリのBot・Workflow一覧へは自動登録されません。読取・実行の方法と必要スキルを`docs/ai-development/README.md`で確認してください。
- ラベルの自動監視、次工程の自動起動、マージ後の自動ラベル更新はありません。工程ごとに明示依頼が必要です。
- 必須CI、保護ルール、権限設定の実環境での有効性は別途確認が必要です。プロンプトだけでは機械的強制を保証しません。
- この資料作成・更新では、GitHub設定変更やWorkflowの試行はしていません。

## 2. 全体フロー

チームでは、業務・要件担当が顧客と要件を確認してIssue化し、設計・開発担当がそのIssueを受け取って設計・開発を進めます。
業務・要件担当に詳細な技術設計を求めず、設計・開発担当は業務判断を独断で補完しません。業務上の追加確認は要件担当を通じて必要に応じ顧客へ戻し、重要な決定はIssueにも反映します。
技術設計は技術に詳しい人間が確認・承認し、業務上の仕様変更は要件担当が確認します。承認者・技術レビュアー・マージ権限者は案件で定めます。

社内説明用の役割別フロー・引き継ぎチェックリストは、次の資料にまとめています。
`docs/ai-development/team-collaboration-guide.md`

```text
【業務・要件担当／mainのworktree】顧客と要件確認 → 要件・対象を示してIssue作成Workflowを依頼
  ＋ ユーザー自身がinterview-to-issueを明示起動
    ↓ 要件確認・Issue一覧全体への同意・Issue作成
  Spec（設計待ち）
    ↓ Issue URL・顧客確認済み内容・業務上の確認窓口を引き渡す
    ↓ 人間がIssue専用の別worktreeを用意
【設計・開発担当／Issue専用worktree】Issueを受け取り、設計Workflowを明示依頼
  Design（設計・設計確認）
    ↓ 技術に詳しい承認者が設計を確認。業務上の追加決定は要件担当へ確認
    ↓ 保存後の設計承認・Issueとの整合確認
  Todo（設計承認済み）
    ↓ 同じ専用worktreeで承認済み設計書を確認
    ↓ 開発Workflowを明示依頼・開始条件確認
  Imp（同じ専任担当が実装・検証・自己レビュー）
    ↓ 提出ゲート通過後、主エージェントがcommit → push → PR作成
  Review（PR提出済み・CI／人間レビュー待ち）
    ├─ 修正確定 → Rework → 検証・自己レビュー → commit・push → Review
    ↓ レビュー対応Workflowで最新headの全条件を確認
  MergeReady（人間のマージ待ち）
    ↓ 人間がマージ ＋ マージ後の再確認を明示依頼
  Done（対象PRのマージ確認済み）

提出のcommit・push・PR作成失敗等 → Error
  → 明示再開依頼・成功済み操作を確認 → 未完了だけ再開

MergeReady後のhead更新等 → 条件を再評価してReviewへ
新たな修正が確定 → Reworkへ
```

矢印は自動処理ではありません。終了報告を受け、次の入力を用意して依頼します。設計差し戻しも人間に確認し、ラベルを勝手に巻き戻しません。

## 3. 役割分担

| 役割 | 担当すること | 境界 |
| --- | --- | --- |
| 人間（依頼者・レビュアー） | 要件・重要仕様の決定、設計承認、worktree作成、権限・環境準備、人間レビュー、マージ、工程ごとの依頼 | AI自己レビューを人間の承認として扱わない |
| 主エージェント | 工程管理、要件・設計工程、Issue・設計書・担当の対応確認、許可範囲内の外部更新、専任担当への依頼、証拠照合、commit・push・PR提出・対応報告 | 開発の実装担当を兼ねない。人間の承認・マージを代行しない |
| 専任担当（サブエージェント） | 同じIssueの実装・テスト・自己レビュー・PR指摘修正、差分と検証結果の報告 | 再委任・外部提出をしない。commit・push・外部更新は主エージェントが担当 |
| CI・権限制御 | 実際に設定された検証・保護ルールの適用 | 定義文書だけでは導入されない |

開発は **1 Issue・1 worktree・1専任担当** が原則です。担当は `async: false` の前景実行で起動し、PR指摘修正まで同じ担当を再開します。再開できなければ停止し、人間の判断を待ちます。別担当・別CLIへ自動切り替えしません。人間による明示的な交代承認、旧担当の停止確認、引き継ぎ証拠と再検証が揃う場合だけ交代できます（第15節）。

## 4. 9種類の工程ラベルと設定条件

工程ラベルは **Issueに1つだけ** 付け、分類ラベルは維持します。PRに同じ工程ラベルを二重管理せず、実際のCI・レビュー・マージ状態を証拠にします。変更後は再取得し、更新を確認するまで次へ進みません。

| ラベル | 意味 | 設定条件・証拠 |
| --- | --- | --- |
| `Spec` | Issue作成済み・設計待ち | 本文への合意とIssue作成を確認し、本文・URL・ラベルを再取得できる |
| `Design` | 設計・設計確認中 | 設計Workflowの依頼・開始条件を確認し、変更・再取得する |
| `Todo` | 設計承認済み | 保存後の設計承認、Issueと採用設計書・テスト方針の整合。worktree等は別途確認 |
| `Imp` | 実装・テスト・提出前自己レビュー中 | 開発開始条件を満たし、変更・再取得後に担当へ依頼する |
| `Review` | PR提出済み・CI／レビュー待ち | PRの存在、対象Issue、head/base、最新コミットと提出結果を確認。修正提出後も戻る先 |
| `Rework` | PR指摘修正・再検証中 | 修正が必要な指摘と対応範囲が確定した |
| `MergeReady` | 人間のマージ待ち | 最新head SHAの必須CI・必要な人間レビュー・未解決指摘・競合・保護ルール等を確認 |
| `Done` | 対象PRのマージ確認済み | 人間のマージ後、明示再確認依頼に基づきmerged状態・マージ先・マージコミット・Issue対応を取得 |
| `Error` | 提出工程の失敗 | commit・push・PR作成の失敗・承認拒否・実行阻害等を記録し、許可される場合だけ変更・再取得 |

環境不足・仕様確認・テスト失敗をすべて `Error` にしません。設計中は `Design`、開発中は `Imp`、指摘修正中は `Rework` を維持します。`MergeReady` はマージの代行ではなく、`Done` は本番配備完了ではありません。

## 5. 4つのWorkflow

### 5.1 issue-creation：要件確認からIssue作成

- **入力**：対象リポジトリの `main` のworktree、要件、実行依頼、ユーザー自身によるスキルの明示起動。
- **操作**：`interview-to-issue` の定義を確認し、一問ずつ目的、要件、検証可能な完了条件、対象外、依存関係を整理。Issue一覧全体への明示同意後に作成します。
- **出力**：Issue URL、合意仕様、再取得した本文・ラベル、未解決事項、次工程。
- **正常終了**：Issueが存在し、工程ラベルが `Spec` だけであることを確認して報告。設計は自動開始しません。
- **範囲外**：設計、実装、worktree作成、commit・push・PR作成、ラベル定義の新設。

`interview-to-issue` は手動ロード専用です。Workflowの依頼だけでは起動しません。ユーザーが次の形式で明示起動します。

```text
/skill:interview-to-issue <要件>
```

取得した既存ラベルに `Spec` があれば初期工程として提案し、一覧への同意に含めます。存在しなければスキル内で作りません。ラベルなし作成にユーザーが同意した場合だけ、その契約内でIssueを作成できますが、作成後は「Spec設定未完了」で停止します。状態未設定のまま設計開始可能とは扱いません。ローカルMarkdownだけの成果物もGitHub Issue作成完了ではありません。

### 5.2 issue-specification：作成済みIssueの設計

- **入力**：Issue URL、実行依頼、人間が用意した当該Issue専用の別worktree。既存設計書があれば参照先・承認状況。
- **操作**：本文・全対象コメント・受け入れ条件・対象外を確認。通常 `Spec` から `Design` へ変更・再取得し、既存コードを調査して `clarify-spec` の契約に従い対話・文書化します。
- **出力**：通常・高リスクではリポジトリルートの `specs/` に新規保存した要件確認書・設計書、採用版、承認記録、公開・未コミット状態、次工程。軽微案件では承認済みのIssue内簡易設計で代替できます（第16節）。
- **正常終了**：保存後の設計承認、重要仕様のIssue反映・再取得、テスト方針との整合確認を終え、`Todo` だけであることを再取得して報告。
- **範囲外**：新規Issue作成、worktree作成、コード実装、サブエージェント起動、commit・push・PR作成、ラベル新設。

`clarify-spec` 実行中にはラベル更新・Issue編集・委任を持ち込みません。スキルの最終出力前の完了確認と、**保存後の設計承認** は別です。スキル終了後に保存済み設計書を人間へ提示します。実装結果を変える追加決定は人間の確認を得てIssue本文にも反映し、再取得して整合を確認します。外部更新の承認が不足すれば `Design` のまま停止します。

既存設計書は参照資料とし、上書きしません。`Design` 再開時は過去の成果物を確認し、旧 `Todo` 等を無断で設計へ戻しません。`Todo` は開発工程固有の開始条件を満たしたことを意味しません。

### 5.3 issue-delivery：開発・検証からPR提出

- **入力**：対象Issue、実行依頼、人間が作成した専用worktreeの絶対パス・作業ブランチ、承認済み設計書の参照先・承認記録、マージ先（指定時）。
- **操作**：通常 `Todo` から開始。Issue・設計・worktree・担当・既存差分を確認し、`Imp` の再取得後に専任担当へ依頼。実装・検証・自己レビュー後、主エージェントが証拠を照合して提出します。
- **出力**：差分、受け入れ条件への証拠、コマンド結果、自己レビュー記録、担当ID、コミットID、push結果、PR URL、取得時点のCI・レビュー状態、未完了事項。
- **正常終了**：PRの存在・最新コミットと `Review` を再取得して報告。返答を待ち続けず終了します。
- **範囲外**：マージ、Issueの手動クローズ、worktree削除。`Review` 以降はレビュー対応Workflowへ渡し、PRを重複作成しません。

軽微案件は人間が区分・理由・Issue内簡易設計を承認すれば別設計書なしで進められます。それ以外の設計書なし経路には依頼者が理由を明示した例外承認が必要です。なければ設計工程への差し戻しを確認します。`Imp` 再開は同じ担当・過去の証拠、`Error` 再開は失敗工程を確認します。

担当は現在のREADME・設定・受け入れ条件から、必要な単体・E2E・lint・型チェック・ビルド等を決めます。環境不足・不合格・未実行を区別し、テスト削除・無効化・期待値の弱体化はしません。文書のみ等の非該当項目には理由と代替確認を示します。

同じ担当が既存の `double-check-loop` に従いIssue全差分を自己レビューします。各回の差分の版・🔴🟡🟢件数・修正・検証・未解決事項を記録し、最大3サイクル以内に **最終修正後の再確認で🔴🟡ゼロ** を確認します。回数消化・修正だけでは通過せず、枠をリセットしません。既存スキルの修正制限も解除しません。同じ担当の確認を独立レビューとは呼びません。

提出ゲートは、受け入れ条件・設計の確定仕様への証拠、最終差分の必要検証成功、最終自己レビュー通過、重要不整合・権限問題・無関係な変更がないこと、合意した設計変更の必要な反映完了です。未達なら `Imp` を維持します。

通過後、開発・自己レビュー工程を終了し、主エージェントが `git-commit-ja`、`git-push-and-create-merge-request-ja` の各契約に従いcommit → push → PR作成を行います。PRには `Closes #対象番号`、設計書参照、検証結果・未検証範囲・主要な設計変更を記載します。ここで `Done` にはしません。

### 5.4 pr-review-response：PR指摘対応とマージ後確認

- **入力**：Issue・PR、実行依頼、既存worktree・ブランチ・専任担当ID・設計書採用版、人間レビューと必須CIの条件。不明な条件は人間へ確認。
- **操作**：全取得対象レビュー・コメント・未解決スレッドをページ分割も含め取得し、最新head SHA・base・CIを確認。指摘を分類し、修正確定なら `Rework` にして同じ担当へ依頼します。
- **出力**：指摘別の対応箇所・検証・未対応理由、最新SHA、提出・コメント結果、CI・人間レビュー、現在ラベル、残条件。
- **終了**：修正提出後は `Review` に戻して報告し、常時待機しません。最新headの全条件を満たせば `MergeReady`。人間のマージ後は別の明示再確認依頼で `Done` を確認・報告します。
- **範囲外**：新規PR作成、人間の承認代行、マージ、Issueの手動クローズ、worktree削除。

指摘は無条件に採用せず「修正が必要」「質問・仕様確認」「対応不要の提案」に分けます。曖昧・矛盾・範囲外は人間へ返します。修正不要の判断にも技術的根拠を示します。

## 6. 設計書とworktreeの引き渡し

1. Issue作成後、設計に入る前に人間が当該Issue専用の別worktreeを用意し、絶対パスと作業ブランチを伝えます。AIは作成しません。
2. Issue番号、設計書のリポジトリ相対パス・ローカル絶対パス、採用版、保存後の承認記録、確定追加仕様、テスト方針を渡します。
3. 設計から開発・PR提出まで同じworktreeを使い、承認済みの設計書を参照します。主エージェントは参照可能性を確認し、専任担当にも実装前に読ませます。主エージェントだけが読んでも引き渡し完了ではありません。
4. 設計書の未コミット・未公開状態、開始前からある差分、設計書自体の変更・提出可否を明示します。関連資料というだけで自動コミットしません。
5. 候補が複数、指定ファイル欠落、承認不明、重要な矛盾なら停止します。更新日時だけで採用版を選びません。

設計工程はcommit・pushしないため、未公開のローカル設計書も引き渡せます。ただしIssue・PRにはローカル絶対パスや存在しない公開リンクを書きません。GitHubで参照可能なパス・URLを使い、未公開ならその旨を記載します。提出対象外の未コミット資料と提出スキルの「全変更」条件が両立しない場合も、勝手に削除・退避せず停止します。

## 7. PRコメント・承認・最新SHAの違い

### 標準の対応報告と、例外的な保留レビュー送信

標準は「指摘別の対応コメント＋提出コミット＋検証結果」です。`COMMENTED`は完了条件にしません。
`PENDING`／`COMMENTED`は **GitHubレビューの状態** であり、Issueの工程ラベルではありません。所有する保留レビューが実際に存在し、送信が許可される場合だけ例外として扱います。

1. 同じ担当が修正・関連検証・最終差分の `double-check-loop` を完了し、主エージェントが照合します。最大3サイクル・最終修正後の🔴🟡ゼロ等の制限は同じです。
2. 開発・自己レビュー工程を終了し、主エージェントがcommit・既存PRへの通常pushをします。レビュー対応Workflowの専用手順で対象リポジトリ・open PR・head/base・ブランチ・クリーン状態・リモートSHAと祖先関係を確認し、通常push後にremoteとPRのSHA一致を確認します。新規PR用スキルは既存PR検出時にpush前に終了するため、この更新には使いません。force push・履歴改変はしません。
3. リモートとPRの最新head SHAが提出コミットに一致することを確認してから、指摘別の対応結果・検証・未対応事項を報告し、必要な再レビューを依頼します。
4. 自分の保留レビューがある場合だけ、所有とreview IDを確認し、承認範囲内で `COMMENT` イベントにより送信します。その後 `PENDING` から `COMMENTED` になったことを取得で確認します。状態値を直接編集しません。
5. 他人の保留レビューは送信・変更しません。自分の保留レビューがなければ対応コメントを投稿します。送信承認がなければ未実施と報告します。

**COMMENTEDは「コメントを送信した」という事実です。人間の承認、スレッド解決、マージ許可を意味しません。**

### MergeReadyに必要な確認

次をすべて **最新head SHA** に対して確認します。

- 必須CIが成功し、未完了・失敗・結果不明がない。必須CI未設定なら、人間が事前承認した代替ゲートの成功証拠がある。
- 必要な人間レビューを満たし、対応が必要な未解決指摘がない。AI自己レビューだけで代替しない。
- 競合がなく、適用される保護ルール・レビュー失効条件を満たす。
- Issue・設計書との重要不整合がない。

ローカルテスト成功はCI成功ではなく、過去SHAへの承認は最新SHAへの証拠とは限りません。不明・取得不能なら合格にせず `Review` を維持します。新しいコミットで条件が失効した場合は再取得して `Review` へ、修正確定なら `Rework` へ戻します。自動監視はないので、変化の確認には新たな起動・依頼が必要です。

## 8. 人間がマージした後

人間がマージしてもAIが自動で `Done` にすることはありません。レビュー対応Workflowへの明示的な再確認依頼が必要です。

主エージェントが対象PRの `merged`、マージ先、マージコミット、Issueとの対応を取得してから `Done` に変更・再取得します。Issueが自動クローズされてもラベルは別に確認します。未マージで閉じられたPRは `Done` にせず、代替PR・中止等の判断を人間へ返します。マージ後CI失敗等の既知の問題も報告します。

## 9. 停止とErrorからの再開

| 状況 | 対応 |
| --- | --- |
| ラベル不足・権限不足・承認拒否・重要仕様不足 | 勝手に補完・新設・迂回しない。現在値と未完了を報告 |
| 無関係な未コミット変更 | 変更・退避・取り込みせず停止 |
| 担当の起動失敗・再開不能 | 現工程を維持し未着手・未完了を報告。自動交代しない |
| 検証不合格・環境不足・自己レビュー未通過 | 現工程を維持し、未検証を成功と扱わない |
| commit・push・PR作成の失敗・拒否・実行阻害 | その操作で停止。許可される場合だけ `Error` に変更・再取得 |
| Error更新もできない | 現在値と「Error更新未完了」を報告。拒否を別手段で迂回しない |
| 結果不明 | 読み取りでローカルcommit・リモート・既存PR等を確認。盲目的に再実行しない |
| push後のコメント・ラベル更新だけ失敗 | 「コード提出済み・報告等未完了」と区別。重複push・重複投稿しない |

再開には対象Workflowへの明示依頼と、直前工程、同じIssue・worktree・ブランチ・担当ID、成功済み／失敗／結果不明の操作、コミット・PR、未完了・再開先の記録が必要です。

提出だけの再開なら成功済み操作を再利用し、未完了だけを行います。開発側でコード変更が必要なら `Imp` に戻して検証・自己レビューを再実施します。PR指摘修正はレビュー対応Workflowの `Rework` で進めます。既存PRは重複作成しません。

## 11. 旧Todo／Doneからの移行

- 旧 `Done` は「開発・検証完了」、新 `Done` は「対象PRのマージ確認済み」です。既存Issueを一括で完了扱いせず、PRの実態と人間の判断で分類し直します。
- 旧 `Todo` は設計承認済みとは限りません。設計書・承認記録・Issue整合を確認し、必要なら人間に確認して `Spec`／`Design` へ差し戻します。
- 進行中の `Imp` は過去の証拠と同じ担当を確認して再開します。
- 名称・説明の整備は別の明示依頼・承認で実施します。通常のIssue作業中に不足ラベルを勝手に作りません。

## 13. FAQ

**Q. 定義の保存・閲覧で実行されますか？**  
いいえ。対象を伴う明示依頼、スキル起動条件、ツール承認が必要です。ラベルや資料の文章も実行許可ではありません。

**Q. Todoならすぐ開発できますか？**  
いいえ。専用worktree、同じ承認済み設計書、既存差分、ブランチ・担当の対応等を確認します。

**Q. PR作成でDoneですか？**  
いいえ。`Review` です。最新SHAのCI・人間レビュー等を満たせば `MergeReady`、人間のマージ後に明示再確認して `Done` です。

**Q. テスト失敗はErrorですか？**  
通常は `Imp`、指摘修正中なら `Rework` を維持します。`Error` は提出工程の失敗を区別する状態です。

**Q. COMMENTEDは承認済みですか？**  
いいえ。コメント送信、人間の承認、スレッド解決、マージ許可は別です。

**Q. 必須CI未設定なら合格ですか？**  
いいえ。人間が事前承認した代替ゲートと成功証拠が必要です。不明な条件を合格扱いしません。

**Q. 担当が再開できなければ交代できますか？**  
自動交代はしません。証拠を報告して停止し、別途人間の明示判断を受けます。

**Q. 設計書が未公開でも進められますか？**  
同じ承認済み採用版を開発worktreeで参照できれば引き渡せます。ただし変更・提出可否を確認し、存在しない公開リンクは作りません。

**Q. マージしたのにラベルが更新されません。**  
自動更新はありません。対象Issue・PRを示してレビュー対応Workflowにマージ後の再確認を依頼してください。

## 14. 定義の照合結果・留意点・一次資料

- `Todo` の「開発着手可能」は、worktree等の確認を免除しません。

## 15. 担当の継続・交代と証拠

担当の記憶だけでなく、次セッションでも参照できる引き継ぎ報告を残します。報告先は案件の承認済み記録先を使い、保存する場合の権限も確認します。新しい台帳を自動作成する必要はありません。

- Issue、リスク区分、設計資料の採用版と人間の承認。
- worktree、ブランチ、担当ID、実際に確認した再開方法、担当の稼働／停止状態。
- HEAD、未コミット差分、テスト実行ログと対象差分、自己レビュー回数・findings。
- PR、指摘ID、最新SHA、成功済みcommit・push・投稿、失敗・結果不明・未完了と再開先。

再開不能なら現在の工程で停止して人間へ報告します。交代は人間が理由・対象・範囲を明示承認した場合だけです。旧担当の停止を確認できない間は新担当を起動しません。
新担当は同じworktreeの唯一の書込担当となり、資料と実差分を読み、必要な検証を再実行します。承認・新旧IDを残し、交代で不合格やレビュー回数をリセットしません。実環境での別セッション再開と承認交代はまだ試験していません。

## 16. リスクに応じた設計の厚さ

| 区分 | 例・判断の目安 | 成果物とゲート |
| --- | --- | --- |
| 軽微 | 誤字や限定的で可逆な修正。外部仕様・データ・認証・プライバシー影響なし | Issue内に変更方針・影響・テスト方針・対象外を記載し、人間が区分と簡易設計を承認 |
| 通常 | 一般的な機能追加・不具合修正 | 簡潔な設計書と人間の設計承認 |
| 高リスク | 認証・権限・機密／個人情報・破壊的変更・データ移行・重要な互換性変更 | 詳細設計と、必要な専門レビュー・移行／復旧計画・承認者を開始前に確定 |

AIは区分と理由を提案しますが、人間が承認します。軽微でも設計Workflowで確認し、`Design → Todo`の証拠を残します。軽微経路は`clarify-spec`を起動しない選択であり、起動後の保存ルールを免除するものではありません。
別設計書を省略しても、必要な検証・自己レビュー・CI／人間レビューを省略しません。資料参照の「設計書」は承認済みIssue内簡易設計へ読み替え、存在しないパスを生成しません。既知の重大問題を後工程へ付け替えてゲートを通過させません。

## 17. 他案件への展開と案件別設定表

構成は「共通原則＋案件別設定＋4 Workflow」です。汎用実行エンジンや設定読込機構は追加しません。現定義はjcbc-demo固定のため、他案件では別Bot・別Workflowとして対象と参照を調整します。新たな社内共通標準として採用する場合の責任者・承認者・適用日・顧客合意は未確定で、ここで承認済みとしません。

案件別の値と未確認事項の正本は`docs/ai-development/project-settings.md`です。本ガイドに同じ値の表を重複管理せず、他案件では同ファイルを基に対象・設計承認・検証・CI・レビュー・担当継続・状態管理・情報管理・導入承認・マージ後の条件を人間が確定します。

小規模案件では9状態を維持する案が分かりやすい一方、大規模ではProjectsの状態欄を正本にする案もあります。二重の正本を持たず、移行時に状態対応と承認を決めます。標準化による手戻り削減だけでなく、設計承認・レビュー・環境整備・モデル利用の費用と負担も試行で評価します。

## 18. 保留・中止・重複

これらは工程とは別の分類です。人間が分類名・理由・再開条件、または重複先を確定し、最後の工程を維持して停止します。分類ラベルがなければ記録で明示し、勝手に新設しません。
停止中は通常の状態遷移・実装・提出を行わず、明示的な再開依頼後に実状態を再確認します。中止・重複で未マージの案件を`Done`にせず、Issue／PRのクローズは人間が行います。`Error`へまとめません。

## 19. 本格運用開始の確認手順

本ガイドは本格運用で使う手順の正本です。文書の整備・運用の希望・試行承認・本格運用承認は、それぞれ別です。運用段階と承認記録は案件別設定で確認します。

### 19.1 試行開始前（導入前）

1. 資料の採用版と読込、全9工程ラベルの名前・説明と旧状態の移行状況、スキル・CLI・認証・権限、必須CI・人間レビュー・保護ルール、リスク・情報管理条件を読み取りで確認し、確認先と未達事項を記録する。ラベルの変更や既存Issueの移行は、必要な範囲を明示して別途承認を得る。
2. 人間が試行対象（#17とは別の小さな要件）、実施者・担当、許可する工程・操作、記録先を事前承認し、承認者・日時・適用SHA・承認記録を残す。この承認までは読み取り・文書確認と別途承認された準備に限り、Issue作成、ラベル変更、設計書の保存、実装、commit・push・PR作成など、工程の書き込み・状態遷移は行わない。

### 19.2 承認済み試行

1. 本格運用の承認を待たず、試行で許可された範囲内で進める。`main` のworktreeで要件整理とGitHub Issue作成を行う。Issue作成後に人間が当該Issue専用の別worktreeを用意し、仕様書作成・設計承認・実装・検証・PR提出まで同じworktreeで進める。`main` では仕様書作成・実装を行わない。
2. 小さな試行Issueで、作成 → 設計承認 → 開発 → PR → 実際の指摘修正 → 既存PR更新 → 再レビュー → 人間によるマージ → `Done` 確認まで一巡する。各工程の承認を省略せず、設計承認前は `Todo` にしない。変更後のラベル再取得、必須CI・人間レビュー、人間によるマージを維持する。
3. 同じ担当の別セッションでの再開、再開不能時の承認付き交代、提出失敗・結果不明からの状態確認と復旧を、承認された安全な方法で検証する。実PRへ無断で障害を注入しない。実施者・日時・対象SHA・結果・未完了事項と証拠の参照先を記録する。
4. 段階・承認・許可範囲を確認できない場合は工程の書き込み・状態遷移前に停止する。工程固有の条件が未達・取得不能なら、該当する操作（提出、`MergeReady`・`Done` への更新など）の前で止め、未確認の項目と再開条件を記録する。

### 19.3 本格運用の承認と開始後

1. 人間が事前確認と試行の証拠を確認し、未達・取得不能の必須条件が残っていれば開始を承認しない。承認する場合は、承認者・日時・適用SHA・適用範囲・証拠の参照先を記録する。試行の成功や文書PRのマージだけで本格運用を開始しない。
2. 明示承認後はその範囲内で通常運用を開始し、Issueごとに導入試行や本格運用の再承認は求めない。各工程の承認・検証は維持し、利用中に見つかった文書の改善は別の変更として扱う。#17を再開する場合は、改修後の採用コミットと本格運用の承認記録を指定し、改めて設計を依頼する。

## 20. マージ以降の境界と利用スキル

`Done`はマージ確認済みであって、リリース承認・配備・DB移行・ロールバック・本番動作確認・監視の完了ではありません。これらが必要な案件では責任者・条件・証拠・停止／復旧を別運用に定義し、未定のまま本番配備しません。

| 工程 | 明示利用するスキル／共通Workflow |
| --- | --- |
| Issue作成 | `interview-to-issue`（ユーザー明示起動） |
| 通常・高リスク設計 | `clarify-spec`、その先行スキル`expert-mode-ja` |
| 軽微設計 | 人間承認付きIssue内簡易設計。`clarify-spec`非起動経路 |
