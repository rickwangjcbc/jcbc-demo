# 要件が分かる人と技術が分かる人で進めるAI開発

> 共有版：リポジトリ内の手順・説明資料です。入口は`docs/ai-development/README.md`、共通ルールは`docs/ai-development/rules.md`、案件別条件は`docs/ai-development/project-settings.md`を参照してください。本文中のパスは明記のない限りリポジトリルート基準です。アプリ登録や権限付与を行うファイルではありません。


## 1. この進め方で実現したいこと

**業務・要件担当が「何を実現したいか」をIssueにまとめ、設計・開発担当が「どう実現するか」を設計し、AIを活用して開発を進めます。**

業務・要件担当に、プログラミングや詳細な技術設計の知識は求めません。一方、設計・開発担当も、顧客の意図を推測して仕様を決めません。Issueを共通の受け渡し資料にして、不明点は担当同士で確認します。

本資料は既存の1 Bot・4 Workflowをチームで使うための説明です。新たな権限や自動処理を追加するものではありません。実際の承認者・マージ権限者は案件で決めます。

## 2. チームの役割

| 役割 | 得意なこと | 主に担当すること | 求めないこと |
| --- | --- | --- | --- |
| 業務・要件担当 | 顧客の業務、困りごと、利用場面、期待する結果の理解 | 顧客への要件確認、Issue内容の確認、業務上の追加質問への回答、完成した動きの業務観点での確認 | コードの詳細理解、DBやAPIなどの技術設計、技術レビュー |
| 設計・開発担当 | システム構成、設計、実装、テスト、技術的なリスクの理解 | Issueの受入確認、設計書作成の指示と技術確認、開発準備、AIへの開発依頼、検証結果確認、PR指摘対応 | 顧客の希望・業務ルールを独断で変更すること |

技術レビュー・マージは、案件で権限を持つ人間が担当します。必要なら設計・開発担当とは別のレビュアーを置きます。上記は役割の区分であり、人数や独立承認の要件を緩和するものではありません。

AIは両者を補助します。**AIが作成したIssue・設計書・コードは、人間の確認の代わりにはなりません。**

## 3. 全体フロー：Issueを境に主担当を引き継ぐ

```text
【業務・要件担当が主担当】
お客様と「困りごと・欲しい動き・完了の条件」を確認
    ↓
AIと対話し、Issueの案を作る
    ↓ 内容を確認し、Issue作成に同意
Issueを作成【Spec：設計待ち】
    │
    │ 引き渡すもの：Issue URL・顧客確認済みの内容・確認窓口
    ▼
【設計・開発担当が主担当】
Issueを読み、設計に着手【Design：設計中】
    ├─ 業務上の不明点 → 業務・要件担当 → 必要ならお客様へ確認
    │                      ↓ 確定内容をIssueにも反映
    └─ 技術的な判断 → 設計・開発担当が確認
    ↓
AIと設計書を作成し、人間が内容を承認【Todo：設計完了】
    ↓ 技術は技術に詳しい承認者、業務上の変更は業務・要件担当が確認
人間が専用の作業場所を準備し、AIへ開発を依頼
    ↓
AIが採用方式に従って実装・テスト・レビュー【Imp：開発中】
    ↓ 主エージェントが提出ゲートを確認
PRを作成【Review：レビュー待ち】
    ├─ 技術的な確認・指摘 → 設計・開発担当／技術レビュアー
    ├─ 動きが要件どおりか → 必要な時点で業務・要件担当が確認
    └─ 修正が必要 → 採用方式に従い、承認された修正と再検証【Rework】→ Review
    ↓ 必須CI・必要な人間レビューなどを確認
【MergeReady：人間のマージ待ち】
    ↓ 権限を持つ人間がマージ
AIにマージ結果の再確認を依頼【Done：マージ確認済み】
```

矢印は自動処理ではありません。各工程の担当者がWorkflowを明示的に依頼します。要件担当から技術担当へ移っても、顧客への確認窓口は残します。

## 4. 工程ごとに「誰が、何を確認するか」

| 工程 | 主な人間の担当 | AIに依頼するWorkflow | 人間が確認する内容 | 次へ渡すもの |
| --- | --- | --- | --- | --- |
| 顧客確認・Issue化 | 業務・要件担当 | `issue-creation` | 課題、期待する動き、完了条件、対象外が顧客意図と合うか | 確認済みIssue、`Spec` |
| 設計 | 設計・開発担当 | `issue-specification` | 実現方法・影響・失敗時動作・テストが妥当か。業務判断は要件担当へ確認 | 承認済み設計資料、`Todo` |
| 開発・PR作成 | 設計・開発担当 | `issue-delivery` | Issue・設計との一致、テスト結果、残課題、提出内容 | PR、検証結果、`Review` |
| PR指摘対応 | 設計・開発担当と必要なレビュアー | `pr-review-response` | 指摘への対応、最新コードのCI、人間レビュー条件 | 修正済みPR、条件充足時に`MergeReady` |
| マージ・結果確認 | 権限を持つ人間／設計・開発担当 | マージ後に`pr-review-response`で再確認 | 正しいPRが正しいマージ先へ取り込まれたか | `Done`と結果報告 |

設計の技術的な承認者、業務上の変更を承認する人、人間レビュアー、マージ権限者は着手前に決めます。業務・要件担当に、理解できない技術設計への包括承認を求めません。

業務観点の動作確認が受け入れ条件に必要な案件では、実施時点・確認者・証拠を先に決め、必要な確認が未実施のままマージ可能とは扱いません。顧客自身の受入試験や本番配備が必要なら、別途その工程を定義します。

## 5. 業務・要件担当がIssueにまとめる内容

技術用語より、**具体的な利用場面と、確認できる結果**を優先します。

| 確認項目 | 例：お問い合わせ一覧の並べ替え |
| --- | --- |
| 背景・目的 | 新しいお問い合わせから確認したい |
| 利用者と場面 | お問い合わせの担当者が、毎朝の確認で使う |
| 欲しい動き | 新しい順・古い順を選べる。選んだらすぐ並び替わる |
| 完了条件 | 初期は新しい順。切り替え後も検索条件と未保存メモが残る |
| 例外 | 日時のない過去データをどう扱うか確認する |
| 対象外 | 優先度順の並べ替え、過去の登録日時の復元はしない |

これは説明用の例であり、新しいIssueや追加要件の承認ではありません。

AIが質問するので、分からない業務判断は顧客に確認します。技術的な実現性が判断できない場合は設計・開発担当へ相談し、AIの推測を顧客の合意として記録しません。設計時に新たな業務判断が出ることはありますが、既知の重要な未決定事項を隠して引き渡しません。

## 6. 引き継ぎチェックリスト

### 業務・要件担当 → 設計・開発担当

- [ ] Issue URLがあり、確認対象の本文を特定できる。
- [ ] 背景・要件・検証できる完了条件・対象外・依存関係が記載されている。
- [ ] 何を顧客に確認済みか、社内での作成同意と顧客合意を区別できる。
- [ ] 未解決事項と業務上の問い合わせ先が分かる。
- [ ] `Spec`の設定を確認している。未設定の場合は設定未完了を伝える。
- [ ] 顧客の個人情報・機密情報を、許可なくAIやIssueへ入力していない。

### 設計・開発担当が受け取った後

- [ ] Issueを読み、不明点を整理する。顧客の意図を勝手に補完しない。
- [ ] リスク区分と設計の厚さ、必要な承認者を確認する。
- [ ] 設計時の業務上の追加決定を要件担当へ返し、確定後はIssueにも反映する。
- [ ] 技術的に承認された設計資料と、必要な業務確認を揃える。
- [ ] 専用worktree・ブランチ・設計資料・AI担当の継続情報を準備して開発を依頼する。

## 7. 問い合わせ・差し戻しのルール

| 発見したこと | 確認先 | 進め方 |
| --- | --- | --- |
| 「新しい順」の意味や画面の動きが曖昧 | 業務・要件担当。必要なら顧客 | 回答を記録し、重要な仕様をIssueへ反映してから続ける |
| 技術方式・データの持ち方・テスト方法が不明 | 設計・開発担当／技術承認者 | 既存構成とリスクに沿って判断する |
| 追加要望・当初範囲の変更 | 業務・要件担当と設計・開発担当 | 影響と承認を確認する。別Issueが必要か判断し、黙って追加しない |
| テスト失敗・CI未完了 | 設計・開発担当 | 開発・修正・レビュー工程を維持し、解消または判断待ちを明示する |
| commit・push・PR作成が失敗 | 設計・開発担当／必要な権限管理者 | 成功済みと未完了を区別し、許可範囲で`Error`。最初から重複実行しない |

**「Issueを渡したら要件担当は関わらない」「AIが作ったから技術確認は不要」という運用にはしません。**

## 8. AIとの役割分担を簡単に説明すると

- **人間の業務・要件担当**：何が必要か、何をもって正しいとするかを確認する。
- **人間の設計・開発担当**：どう作るか、技術的に安全で要件に合うかを確認する。
- **主エージェント**：手順と資料を管理し、許可された提出操作と報告を行う。
- **作業担当**：標準の前景再開方式と同一対話セッション方式では、同じ専任担当が実装・テスト・自己レビュー・指摘修正を行う。R2と案件別設定で検証・事前承認された工程別引き継ぎ方式では、同じIssue専用worktreeで工程ごとに新しい前景セッションへ引き継ぐ。レビューは読み取り専用で、書込担当は同時に1人だけとする。
- **権限を持つ人間**：必要な承認と最終マージを行う。

人間同士の引き継ぎとAI担当の継続は別です。要件担当と技術担当が別の会話・端末を使う場合でも、Issue・設計資料・承認記録を明示して渡します。開発開始後はAI担当ID・作業場所・検証結果も残し、人間の担当が変わっただけで別AIを重複起動しません。

## 9. まず覚える状態

| 覚え方 | ラベル |
| --- | --- |
| 要件をIssueにしたので、技術担当へ渡せる | `Spec` |
| 技術担当が設計を進めている | `Design` |
| 必要な設計承認が揃った | `Todo` |
| 開発している | `Imp` |
| PRの確認待ち | `Review` |
| 指摘を直している | `Rework` |
| マージ条件が揃い、人間の操作待ち | `MergeReady` |
| 人間のマージを確認した | `Done` |
| 提出工程が失敗している | `Error` |

ラベルは担当者の作業を助ける目印です。ラベルだけで承認済み・自動実行可能とは判断しません。

## 10. 説明会でのまとめ

> お客様の業務が分かる人が、AIと一緒に「何を実現したいか」をIssueにします。
> 技術が分かる人が、そのIssueを受け取って設計し、AIを活用して開発・テスト・PR提出を進めます。
> 業務判断は要件担当へ、技術判断は技術担当へ戻します。
> 最後は必要な確認を揃え、権限を持つ人間がマージします。

## 11. 利用開始前の注意と詳細資料

本資料作成では、Bot・Workflowの実行定義、GitHubラベル、権限、CIを変更していません。ラベルの実設定、リポジトリのルール・手順書の読込、担当の別セッション再開、一連の実動作は別途確認が必要です。各工程は明示依頼と必要なツール承認の範囲で行います。

`interview-to-issue`はユーザーによる`/skill:interview-to-issue <要件>`の明示起動が必要です。要件担当がGitHubの作業場所・権限の準備に不慣れな場合は、設計・開発担当が初期準備を支援します。技術知識を求めないことは、準備や承認を自動的に省略できることを意味しません。

軽微な修正は承認済みのIssue内簡易設計で代替できます。`Done`はマージ確認であり、顧客の最終検収・リリース・本番配備の完了を意味しません。

詳細な操作、依頼文例、リスク区分、停止・再開は、次の既存ガイドを参照してください。
`docs/ai-development/lifecycle-guide.md`
