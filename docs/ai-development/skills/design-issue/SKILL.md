# Issueの設計を進める

入力は単一のIssue番号（例：`#42`）またはIssue URL。例：

```text
/skill:design-issue #42
```

1. 設計が明示依頼され、対象が一件に決まることを確認する。番号は案件設定のリポジトリに対して解決し、URL指定時はリポジトリが一致することを確認する。ファイルの閲覧やコマンドの引用だけでは開始しない。
2. 手順の正本はリポジトリルート基準の `docs/ai-development/workflows/issue-specification.md`。Botプロンプトの `repository`、`readme_path`、`rules_path`、`project_settings_path` を確認し、作業場所の `origin` と依頼対象を照合する。以下の「Issue単位で採用版を確定する」に従い、確定したコミットの `AGENTS.md`、設定で指定された3資料、この工程の手順書を全文読む。案件別設定の対象も照合する。設定不足、資料の取得不能、対象の不一致、上位制約との衝突があれば、作業ツリー版・ローカル `HEAD`・登録済みWorkflowで代用せず、書き込み前に停止する。
3. 手順書に沿ってIssueの実在・本文・全対象コメント・工程ラベル、保留・中止の有無、人間が用意したIssue専用の別worktree（`main` 以外）と既存差分を確認する。R5・R8と案件別設定に従い、対象範囲・権限・必要な操作承認を確認する。必要な条件を確認できなければ、承認コメントの代理投稿を含む書き込み・状態遷移前に停止する。新規設計は `Spec` から。`Design` からは、再開の明示依頼を受け、既存の成果物・未完了事項を照合してから再開する。Issueや設定で確認できない必須情報と業務判断だけを尋ねる。
4. 通常・高リスク案件では `expert-mode-ja` と `clarify-spec` の条件を維持する。軽微案件でも人間によるIssue内簡易設計の承認が必要。保存だけでは `Todo` に変更せず、人間が対象Issueと採用設計版を承認し、整合・適用ゲート・必要な操作承認を確認できた場合に限り変更して再取得する。実装や次工程は自動で開始しない。

## Issue単位で採用版を確定する

- 対象Issueの本文と全コメントを読み取り、当該Issueの採用版の承認記録を探す。記録には対象Issue、完全なコミットSHA、承認者と明示承認を確認できる根拠が必要。同じ会話での確認済みの承認も使える。記録の取得が不完全、承認の根拠を確認できない、または記録が食い違う場合は、「記録なし」とみなさず停止する。
- 承認済みの版がない場合だけ、対象リポジトリのGitHub上の `main` の完全なコミットSHAを取得する。対象Issue、候補SHA、読めた資料を示し、「この版で設計を進めてよいですか？」と確認する。利用者にSHAの調査や再入力を求めず、明示承認を待つ。候補取得や資料確認ができなければ設計に進まない。返答後は提示したSHAを使い、`main` を取り直して置き換えない。
- 別チャットでも再利用できるよう、承認者本人が対象Issueのコメントに `設計手順の採用版: <完全なSHA> を承認します` と記録する。代理投稿は、手順3の対象範囲・権限と対象操作の許可を確認した後、承認者と承認の根拠を確認できる参照先を添え、投稿内容と対象Issueへの書き込みについて別途明示許可を得た場合のみ行う。採用版の承認だけで投稿しない。未記録なら、同じ会話では承認を再利用できるが別チャットでは再確認が必要と伝える。
- 確定した版は同じIssueの再開時に再利用し、案件共通SHAは使わない。設計の途中で最新の `main` に自動で切り替えない。採用版への承認と、保存した設計資料への承認は別に扱う。
