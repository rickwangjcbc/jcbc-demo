# Issueの設計を進める

入力は単一のIssue番号（例：`#42`）またはIssue URL。例：

```text
/skill:design-issue #42
```

1. 設計が明示依頼され、対象が一件に決まることを確認する。番号は案件設定のリポジトリに対して解決し、URL指定時はリポジトリが一致することを確認する。ファイルの閲覧やコマンドの引用だけでは開始しない。
2. 手順の正本はリポジトリルート基準の `docs/ai-development/workflows/issue-specification.md`。Botプロンプトの `repository`、`readme_path`、`rules_path`、`project_settings_path` と、人間が確認した採用コミットを使う。同じ会話で確認済みの値は再利用し、分からない値だけを尋ねる。採用コミットの `AGENTS.md`、設定で指定された3資料、この工程の手順書を全文読む。作業場所の `origin`、案件別設定の対象、依頼対象を照合する。設定不足、採用版や資料の取得不能、対象の不一致、上位制約との衝突があれば、作業ツリー版・最新 `HEAD`・登録済みWorkflowで代用せず、書き込み前に停止する。
3. 手順書に沿ってIssueの実在・本文・全対象コメント・工程ラベル、保留・中止の有無、保存先と既存差分を確認する。新規設計は `Spec` から。`Design` からは、再開の明示依頼を受け、既存の成果物・未完了事項を照合してから再開する。Issueや設定で確認できない必須情報と業務判断だけを尋ねる。
4. 通常・高リスク案件では `expert-mode-ja` と `clarify-spec` の条件を維持する。軽微案件でも人間によるIssue内簡易設計の承認が必要。保存だけでは `Todo` に変更せず、人間が対象Issueと採用設計版を承認し、整合・適用ゲート・必要な操作承認を確認できた場合に限り変更して再取得する。実装や次工程は自動で開始しない。
