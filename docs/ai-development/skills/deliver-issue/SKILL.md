# Issueの開発・初回PR提出を進める

設計に使ったIssue専用worktreeで、単一のIssue番号またはURLを指定する。

```text
/skill:deliver-issue #42
```

工程別引き継ぎ方式では、人間が対象Issue・採用するルールのコミット・方式を開発依頼で明示する。

```text
/skill:deliver-issue #42 採用ルールは <コミットSHA>。工程別引き継ぎ方式で進めてください。
```

1. **対象と採用版を確定する。** ファイルの閲覧やコマンドの引用は実行依頼とみなさない。番号はBotプロンプトの `repository` 内のIssueとして解決し、URL指定時もリポジトリの一致を確認する。対象Issue・作業場所の `origin`・案件設定を照合する。採用ルールのコミットはIssue単位の承認記録から確認し、設計書の採用版や実装の `HEAD` と区別する。承認記録を取得できない、または記録が矛盾する場合は停止する。記録がないと確認できた場合だけ、GitHub上の `main` の完全なSHAを候補として提示し、人間の明示承認を待つ。途中で最新版に自動で切り替えない。
2. **手順書の開始条件を確認する。** 確定したコミットの `AGENTS.md`、Botプロンプトの `readme_path`・`rules_path`・`project_settings_path` が指す資料、および `docs/ai-development/workflows/issue-delivery.md` を全文読み、適用する。登録済みの `demo-issue-delivery` は起動しない。通常は `Todo` から開始する。承認済み設計と承認記録、リスク区分、設計に使った同じIssue専用worktree・ブランチ、既存差分、必要な権限と操作承認を照合し、確認済みの値は聞き直さない。継続方式はR2と案件別設定に従い、工程別引き継ぎを推測で選んだり、再開に失敗したときに自動で切り替えたりしない。不足・不一致・利用不能があれば `Imp` への変更や実装の前に停止する。再開時は手順書に従い、完了済みの操作を繰り返さない。
3. **実装・検証後はレビュー依頼を待つ。** 採用方式に従い、実装とローカル検証を同じIssue専用worktreeで行い、対象差分と結果を報告する。各回のレビュー・再レビューには対象差分への明示依頼が必要。指摘の修正には対象差分・指摘番号・修正範囲への別の明示承認を待つ。差分が変わったら旧承認・旧レビュー結果を流用しない。
4. **初回PRは提出条件を満たしたときだけ作る。** 最大3回のAIレビューの範囲内で、同じ最終提出差分の検証成功と赤・黄の指摘ゼロを確認し、利用者からの提出依頼と各操作の承認を得る。主エージェントが提出先と既存PRの有無を提出前・提出スキル起動直前に照合する。既存PRがある、確認できない、または使う提出スキルが既存PRを検出してもpushを止めない場合は起動せず、pushせずに理由を報告する。既存PRの更新は `docs/ai-development/workflows/pr-review-response.md` に基づく別の明示依頼を待つ。新規PR提出後は、手順書に従い提出コミットとPRの最新head、Issueの `Review` を再取得して報告する。マージや `Done` への変更は行わない。
