# Issueの開発・PR提出を進める

設計に使ったIssue専用worktreeで、単一のIssue番号またはURLを指定する。

```text
/skill:deliver-issue #42
```

この短い依頼は実装・ローカル検証の開始依頼とする。採用版の案件別設定で、現在の環境・Botに適用される着手時の既定方式が確認できれば、方式の再入力は不要。工程別引き継ぎを明示指定する場合の例：

```text
/skill:deliver-issue #42 採用ルールは <コミットSHA>。工程別引き継ぎ方式で進めてください。
```

1. **対象と採用版を確定する。** ファイルの閲覧やコマンドの引用は実行依頼とみなさない。番号はBotプロンプトの `repository` 内のIssueとして解決し、URL指定時もリポジトリの一致を確認する。対象Issue・作業場所の `origin`・案件設定を照合する。採用ルールのコミットはIssue単位の承認記録から確認し、設計書の採用版や実装の `HEAD` と区別する。承認記録を取得できない、または記録が矛盾する場合は停止する。記録がないと確認できた場合だけ、GitHub上の `main` の完全なSHAを候補として提示し、人間の明示承認を待つ。途中で最新版に自動で切り替えない。
2. **手順書の開始条件を確認する。** 確定したコミットの `AGENTS.md`、Botプロンプトの `readme_path`・`rules_path`・`project_settings_path` が指す資料、および `docs/ai-development/workflows/issue-delivery.md` を全文読み、適用する。登録済みの `demo-issue-delivery` は起動しない。通常は `Todo` から開始する。承認済み設計と承認記録、リスク区分、設計に使った同じIssue専用worktree・ブランチ、既存差分、必要な権限と操作承認を照合し、確認済みの値は聞き直さない。継続方式は採用版のR2と案件別設定に従い、人間の明示指定または新規着手に適用される既定から確定する。再開では記録済みの方式を使い、推測や失敗時の自動切り替えは行わない。不足・不一致・利用不能があれば `Imp` への変更や実装の前に停止する。再開時は手順書に従い、完了済みの操作を繰り返さない。
3. **実装・検証後はレビュー依頼を待つ。** 採用方式に従い、実装とローカル検証を同じIssue専用worktreeで行い、対象差分と結果を報告する。各回のレビュー・再レビューには対象差分への明示依頼が必要。指摘の修正には対象差分・指摘番号・修正範囲への別の明示承認を待つ。差分が変わったら旧承認・旧レビュー結果を流用しない。
4. **提出は採用版の `issue-delivery.md` 第6節に従う。** 最大3回のAIレビューの範囲内で、同じ最終提出差分の検証成功と、手順書が定めるレビュー条件を確認する。人間が承認・公開許可した版と同一の設計書は、手順書に従って版・許可・範囲を照合し、AI内容再レビューを省いて同梱できる。それ以外のAIレビュー対象は赤・黄の指摘ゼロを確認し、提出依頼と各操作の承認を得る。照会成功で対応するオープンPRが0件なら通常pushし、リモート先端SHAの一致を確認して新規PRを作成する。1件なら対象を照合してそのPRの更新への明示承認を得てから、採用版の `pr-review-response.md` 第3節の専用手順で通常pushとhead確認だけを行う。新規PRは作らない。照会失敗・取得不完全・複数件・対象不一致・未確認の先端更新があればpush前に停止する。結果不明時は再実行前にリモートとPRを再取得する。同梱の新規PR用提出スキルは起動しない。マージや `Done` への変更は行わない。
