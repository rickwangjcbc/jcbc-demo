# double-check-loop：提出前のAIレビュー補助手順

## 適用条件

- [開発・PR提出](issue-delivery.md)と[PRレビュー対応](pr-review-response.md)で共用する補助手順。人間が確認した採用資料SHAの版を使う。作業ツリーにある未採用の草案に切り替えず、版が未確定・取得不能なら停止する。
- リポジトリ内手順書の直接適用を実行環境が許す場合に使い、アプリの同名Workflowは起動しない。同じ担当の方式では実環境の `double-check` の定義を確認する。工程別引き継ぎ方式では下記の専用手順を使い、どちらも上位指示・スキル・ツールの制約を守る。登録が必須、スキルが利用不能、または指示や権限が両立しない場合は現工程で停止し、人間に報告する。別手順・別ツールによる代用や権限拡大はしない。
- 同じ担当の方式では呼出元の専任担当による自己レビューであり、独立レビューではない。工程別引き継ぎ方式の読み取り専用レビューも、必須の人間レビューを代替しない。起動は呼出元の主エージェントが管理し、担当の再委任、主エージェントによる実装代行、担当によるラベル変更・外部更新・commit・pushは行わない。
- 各回の開始・再開時に、自己レビュー、軽量検証、承認後の修正・再テストの実行先が、呼出元で実装・修正したIssue専用worktreeと一致することを確認する。不一致・照合不能なら該当操作の前に停止し、別worktreeの結果で代用しない。

## 提出差分とAI内容レビュー対象の切り分け

- 未追跡の提出対象も含め、最終提出差分全体を特定する。人間による設計承認と提出先への公開許可をそれぞれ確認し、対象Issue・リポジトリ相対パス・承認版の内容識別子（Git blob IDやファイルのSHA-256など）が提出予定の版と一致する設計書だけを、AIによる内容再レビューから除外する。承認記録と公開許可の参照先、照合した版、除外したパスを記録する。拡張子やパスだけでは除外しない。省略対象は設計書の内容再レビューに限る。パス変更・ファイル種別・ファイルモード（実行ビットなど）の変更は、内容が同一でもAIレビュー対象に残す。必要な非内容差分を指定できない場合は、そのパスを一括除外しない。
- 内容が異なる、または同一性を証明できない設計書は除外しない。設計承認や提出先への公開許可が確認できない版は同梱せず、提出に必要なら人間の確認を待つ。AIレビューの通過は設計承認・公開許可の代わりにならない。
- 除外した設計書は実装の参照資料および提出差分全体の照合対象に残す。各方式で、除外後のレビュー対象パス・差分を明示し、全差分や直近コミット等の既定範囲に戻さない。除外を守れないスキル・環境では停止する。除外後に対象がなければレビューを起動せず「対象なし」と記録する。レビューの合格や🔴🟡ゼロとは記録せず、回数も消費しない。必要な検証と人間レビュー・必須CIは省略しない。

## レビューと修正（同じ担当の方式）

1. 呼出元工程の実行依頼とは別に、対象差分を示したユーザーの明示的な `double-check` 実行依頼を各回で待つ。実行依頼は修正承認ではない。
2. 初回提出ではマージ先の取得済みSHAと作業HEADの共通祖先、既存PR更新では取得済みのPRのbaseとheadの共通祖先を基準SHAとして固定する。取得・照合できなければ停止する。明示依頼には、基準SHAからのコミット済み差分、ステージ済み・未ステージ差分、未追跡の提出対象を含む提出差分から、上記に従い切り分けたAIレビュー対象を指定する。未追跡というだけで提出対象に加えない。Issueの受け入れ条件・承認済み設計（PR対応では確定指摘も）に照らして確認し、版を特定したうえで関連する軽量検証のコマンドと結果を記録する。レビューフェーズではファイルを変更しない。
3. スキルの出力形式に従い、findingsを重大度順・通し番号で先に報告し、確認範囲・検証結果・残リスクを示す。🔴または🟡があれば、修正可能な指摘と修正できない理由を示してから、末尾にスキル所定の修正確認を出す。確認の出力は編集許可ではなく、事前承認は使わない。🟢のみ、または指摘なしなら修正確認を出さない。
4. 報告後に対象版と指摘に対する明示承認があり、再確認枠が残る場合だけ、スキル所定の「> double-check モードを終了し、修正フェーズに移ります。」を出力して、承認範囲の🔴🟡を修正する。🟢を含む承認を🔴🟡だけの承認に読み替えず、対象を確認する。🟢はこのループでは記録のみとし、対応は別依頼とする。3回目に🔴🟡が残った場合は承認があっても編集・提出しない。修正は既存ファイルの `edit` と検証等に必要最小限の `bash` に限る。新規ファイル作成・削除、依存の追加・更新、範囲外変更、破壊的操作は禁止。スキル内で修正できない指摘は未解決として呼出元へ返す。再確認枠が残り、別の明示依頼と操作承認がある場合に限り、同じ担当が呼出元の開発・修正工程で許可範囲の対応を行える。回数はリセットしない。新たな問題の発見時は対象を勝手に広げず、スキル所定の確認を行う。承認なし・曖昧・拒否の場合は編集しない。
5. 修正後はレビュー時と同じテストを再実行し、修正後の結果を分けて報告する。再実行で不合格なら内容に応じて🔴または🟡の新たなfindingとして扱い、追加修正や `edit` での書き戻しにはスキル所定の確認と別途の明示承認を必要とする。再実行できなければ理由と未検証範囲を記録する。テスト再実行だけでは再レビューにならない。修正後は提出差分全体と除外条件を照合し直し、切り分けたAIレビュー対象を次の明示的な実行依頼を受けて手順1から再確認する。自動起動せず、承認は次回に持ち越さない。

## レビューと修正（工程別引き継ぎ方式）

1. R2・案件別設定に従い、開発着手時に確定した対象Issue・採用ルールのコミット・工程別引き継ぎ方式とその選択根拠の記録と、使用する環境との両立を確認する。同梱の `double-check` による同一実行内の修正移行を、別セッションへの承認や編集許可として扱わない。環境上その契約が必須で読み取り専用レビューと別修正に分けられない場合は停止する。
2. 各回で、人間から対象差分版を指定したレビューの明示依頼を待つ。共通祖先を基準SHAとして固定し、コミット済み・ステージ済み・未ステージ差分と未追跡の提出対象を特定する。同じIssue専用worktree・承認済み設計・検証結果・R2の引き継ぎ記録を照合し、上記で切り分けたAIレビュー対象を新しい前景（`async: false`）セッション1件に渡す。前の書込担当の終了や対象差分が確認できなければ起動しない。
3. レビュー担当には読み取り専用の権限を適用し、適用を確認できなければ起動しない。担当は受け入れ条件・設計・検証記録と実差分を読み、重大度（🔴🟡🟢）・通し番号・根拠・確認範囲・残リスクを報告して終了する。主エージェントは終了と差分の不変を照合する。担当はファイル・ステージ・外部状態を変えず、副作用のあるテストも行わない。足りない検証は呼出元へ返す。最終差分の検証成功が確認できなければ提出不可とする。
4. 修正は報告後、対象差分版と指摘番号・修正範囲への人間の明示承認があり、再確認枠が残る場合だけ行う。前の書込担当とレビュー担当の終了、対象差分に変化がないことを照合してから、新しい前景セッション1件に、同じworktreeで承認範囲の修正・再検証だけを依頼する。照合不能・差分変更なら停止し、以前の承認を使わない。🟢の対応は別依頼とし、3回目に🔴🟡が残れば編集・提出しない。
5. 修正担当は変更差分・検証結果・未完了事項を返して終了する。再レビューには別の明示依頼が必要。レビューごとに回数を消費し、引き継ぎ・結果不明・担当交代で枠を戻さない。

## 確認待ちと再開

レビュー実行依頼・修正承認を待つときは、担当は現在の呼び出し・ターンを終了して主エージェントへ制御を返す。主エージェントは、待ちの種類、方式、担当IDとセッション識別情報、worktreeとブランチ、対象差分版、指摘番号、消費済み回数と残り枠、検証結果、成功済み／未完了操作を記録する。

ユーザーの返答後、レビューの実行依頼と修正承認を区別し、対象差分版と（修正時は）指摘番号・承認範囲を照合する。標準方式では同じ担当を前景で再開する。R2の検証・採用承認がある同一対話セッション方式では、同じ担当・セッション・worktreeを照合し、その返答で許可された作業だけを次のターンとして送る。工程別引き継ぎ方式では、前担当を再開せず、上記の条件を満たした場合に限り新しい前景セッションを起動する。どの方式でも待機中の自動送信や、修正承認を次のレビュー実行依頼として扱うことはしない。

差分が変わっていれば以前の承認・レビュー結果を流用せず、残り枠内で新しい差分版への明示的なレビュー実行依頼を待つ。再開不能、セッション照合不能、または実行結果不明なら、状態・ログ・実差分を先に確認し、確認なしに依頼を再送しない。続行条件を満たせなければ現工程で停止し、方式・担当・CLIを自動で切り替えない。

## 回数・通過・停止

- 初回レビューを1回目とし、修正後の再確認も1回として最大3レビューサイクル。レビューの途中で結果が不明になっても枠を取り直さず、再開や担当交代で回数をリセットしない。
- 提出できるのは、最終修正後（修正がなければ現在）の提出対象と同じ差分で、必要な検証の成功と、AIレビュー対象での🔴🟡ゼロ（対象が空なら「対象なし」と除外条件の照合）を確認できた場合だけ。差分が変わったら以前の結果を流用しない。3回目に🔴🟡が残れば、次の再確認枠がないためその場で停止し、3回目の指摘を修正しただけでゼロ扱いしない。
- 必要なテストの未実行・不合格・結果不明は区別し、理由、判明している結果、未検証範囲を報告する。いずれも合格にせず、結果不明は状態・ログを先に確認する。文書のみ等でテストが非該当なら、理由と実施した文書照合等の代替証拠を明記する。AIレビューと人間レビュー・必須CIは別の証拠とする。
- 再確認枠・実行依頼・修正承認・権限・必要な検証証拠が不足する場合や、結果不明・未解決の🔴🟡が残る場合は合格にしない。続行条件が揃わなければ現工程（`Imp`／`Rework`）で停止し、ラベルを変えず、提出せずに停止理由と再開条件を報告する。

## 各回で残す証拠

- 最終提出差分全体とAIレビュー対象の範囲を区別し、除外した設計書のパス・提出版の識別子・設計承認と公開許可の参照先・照合結果を記録する。
- サイクル番号・残り枠、担当ID、レビュー・検証を行ったworktree、レビュー対象の差分版（基準SHA・HEAD、未コミット差分の識別情報、未追跡提出対象のパス・内容の識別情報）。修正した場合は修正前後の版を区別する。
- 🔴🟡🟢の件数と指摘番号、修正承認の対象、修正内容・修正済み／未修正の件数。件数が分からなければゼロでなく不明と記録する。
- 検証コマンド・対象版・結果、未実行や結果不明の理由と残リスク、未解決事項・停止理由・再開条件。

主エージェントは担当報告だけで通過とせず、実際の提出対象・差分版・検証記録を照合する。
