# double-check-loop：提出前の自己レビュー補助手順

## 適用条件

- [開発・PR提出](issue-delivery.md)と[PRレビュー対応](pr-review-response.md)で共用する補助手順。人間が確認した採用資料SHAの版を使う。作業ツリーにある未採用の草案に切り替えず、版が未確定・取得不能なら停止する。
- リポジトリ内手順書の直接適用を実行環境が許す場合に使い、アプリの同名Workflowは起動しない。実環境の `double-check` の定義を確認し、上位指示・スキル・ツールの制約を守る。登録が必須、スキルが利用不能、または指示や権限が両立しない場合は現工程で停止し、人間に報告する。別手順・別ツールによる代用や権限拡大はしない。
- 呼出元工程の同じ専任担当が行う自己レビューであり、独立レビューではない。この手順単体では別担当の起動・再委任・主エージェントによる代行を行わない。ラベル変更・外部更新・commit・pushは行わない。

## レビューと修正

1. 呼出元工程の実行依頼とは別に、対象差分を示したユーザーの明示的な `double-check` 実行依頼を各回で待つ。実行依頼は修正承認ではない。
2. 初回提出ではマージ先の取得済みSHAと作業HEADの共通祖先、既存PR更新では取得済みのPRのbaseとheadの共通祖先を基準SHAとして固定する。取得・照合できなければ停止する。明示依頼には基準SHAからのコミット済み差分、ステージ済み・未ステージ差分、未追跡の提出対象を含む全範囲を指定し、直近コミット等の既定範囲で代用しない。未追跡というだけで提出対象に加えない。Issueの受け入れ条件・承認済み設計（PR対応では確定指摘も）に照らして確認し、版を特定したうえで関連する軽量検証のコマンドと結果を記録する。レビューフェーズではファイルを変更しない。
3. スキルの出力形式に従い、findingsを重大度順・通し番号で先に報告し、確認範囲・検証結果・残リスクを示す。🔴または🟡があれば、修正可能な指摘と修正できない理由を示してから、末尾にスキル所定の修正確認を出す。確認の出力は編集許可ではなく、事前承認は使わない。🟢のみ、または指摘なしなら修正確認を出さない。
4. 報告後に対象版と指摘に対する明示承認があり、再確認枠が残る場合だけ、スキル所定の「> double-check モードを終了し、修正フェーズに移ります。」を出力して、承認範囲の🔴🟡を修正する。🟢を含む承認を🔴🟡だけの承認に読み替えず、対象を確認する。🟢はこのループでは記録のみとし、対応は別依頼とする。3回目に🔴🟡が残った場合は承認があっても編集・提出しない。修正は既存ファイルの `edit` と検証等に必要最小限の `bash` に限る。新規ファイル作成・削除、依存の追加・更新、範囲外変更、破壊的操作は禁止。スキル内で修正できない指摘は未解決として呼出元へ返す。再確認枠が残り、別の明示依頼と操作承認がある場合に限り、同じ担当が呼出元の開発・修正工程で許可範囲の対応を行える。回数はリセットしない。新たな問題の発見時は対象を勝手に広げず、スキル所定の確認を行う。承認なし・曖昧・拒否の場合は編集しない。
5. 修正後はレビュー時と同じテストを再実行し、修正後の結果を分けて報告する。再実行で不合格なら内容に応じて🔴または🟡の新たなfindingとして扱い、追加修正や `edit` での書き戻しにはスキル所定の確認と別途の明示承認を必要とする。再実行できなければ理由と未検証範囲を記録する。テスト再実行だけでは再レビューにならない。修正後の全差分は、次の明示的な実行依頼を受けて手順1から再確認する。自動起動せず、承認は次回に持ち越さない。

## 確認待ちと再開

レビュー実行依頼・修正承認を待つときは、担当は前景呼び出し内で待ち続けず、待ち状態・回数・対象差分版・該当する指摘番号を主エージェントに返す。主エージェントはこれらと担当ID・実際に確認した再開方法を保持し、ユーザーの返答を受けてから対象版の同一性と依頼・承認の範囲を照合し、同じ担当を前景で再開する。差分が変わっていれば以前の承認で編集せず、残り枠内で新しい差分版の確認に戻る。再開方法を確認できない、または再開できない場合は現工程で停止し、別担当へ自動交代しない。

## 回数・通過・停止

- 初回レビューを1回目とし、修正後の再確認も1回として最大3レビューサイクル。レビューの途中で結果が不明になっても枠を取り直さず、再開や担当交代で回数をリセットしない。
- 提出できるのは、最終修正後（修正がなければ現在）の提出対象と同じ差分で、必要な検証の成功とレビューでの🔴🟡ゼロを確認できた場合だけ。差分が変わったら以前の結果を流用しない。3回目に🔴🟡が残れば、次の再確認枠がないためその場で停止し、3回目の指摘を修正しただけでゼロ扱いしない。
- 必要なテストの未実行・不合格・結果不明は区別し、理由、判明している結果、未検証範囲を報告する。いずれも合格にせず、結果不明は状態・ログを先に確認する。文書のみ等でテストが非該当なら、理由と実施した文書照合等の代替証拠を明記する。自己レビューと人間レビュー・必須CIは別の証拠とする。
- 再確認枠・実行依頼・修正承認・権限・必要な検証証拠が不足する場合や、結果不明・未解決の🔴🟡が残る場合は合格にしない。続行条件が揃わなければ現工程（`Imp`／`Rework`）で停止し、ラベルを変えず、提出せずに停止理由と再開条件を報告する。

## 各回で残す証拠

- サイクル番号・残り枠、担当ID、レビュー対象の差分版（基準SHA・HEAD、未コミット差分の識別情報、未追跡提出対象のパス・内容の識別情報）。修正した場合は修正前後の版を区別する。
- 🔴🟡🟢の件数と指摘番号、修正承認の対象、修正内容・修正済み／未修正の件数。件数が分からなければゼロでなく不明と記録する。
- 検証コマンド・対象版・結果、未実行や結果不明の理由と残リスク、未解決事項・停止理由・再開条件。

主エージェントは担当報告だけで通過とせず、実際の提出対象・差分版・検証記録を照合する。
