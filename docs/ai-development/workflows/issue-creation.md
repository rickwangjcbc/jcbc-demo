# Issue作成

## 目的と境界

`interview-to-issue`で合意した要件をGitHub Issueにし、設計工程へ渡す。
対象リポジトリは`rickwangjcbc/jcbc-demo`。別の対象を推測しない。
本Workflowの閲覧・編集は実行依頼ではない。実行には対象と要件を伴う明示依頼、スキルの起動条件、ツール承認が必要。
本定義は外部権限や自動起動機構を導入しない。

## 開始入力

- 対象リポジトリを確認できる作業場所と要件。
- 対象についての本Workflowの実行依頼。
- ユーザーによる`/skill:interview-to-issue <要件>`の明示起動。

`interview-to-issue`は手動ロード専用。Workflow実行依頼だけで自動起動しない。
未起動なら上記コマンドを案内し、ユーザーによる明示起動を待つ。

## 手順

Botルールの導入確認・保留／中止を適用する。想定リスクと設計の厚さは設計工程へ引き渡し、軽微案件でも設計判断を省略して直接開発しない。
他案件へ展開する場合は`docs/ai-development/project-settings.md`の案件別設定表を確定し、別定義として適用する。本定義の対象は自動変更しない。

1. 同梱の`interview-to-issue`の定義を全文確認し、起動条件・許可ツール・停止条件に従う。
2. スキルで対象を確認し、要件を一問ずつ明確化する。目的、要件、検証可能な完了条件、対象外、依存関係を確定する。
3. スキルのラベル取得結果に既存の`Spec`がある場合は初期工程として提案し、Issue一覧への同意に含める。他の工程ラベルを併用しない。他の分類ラベルは合意したものを維持する。
4. 一覧全体への明示同意後、スキルでIssueを作成する。作成済みIssueを重複作成しない。失敗時はスキルの規定で停止する。
5. スキル終了後、主エージェントが作成したIssueの本文・URL・ラベルを再取得する。`Spec`が既に付与されていれば更新を繰り返さない。
6. `Spec`が既存ラベルとして存在するが未付与なら、本Workflowの明示依頼と必要な承認の範囲で`Spec`へ変更し、再取得する。他の工程ラベルだけを外し、分類ラベルを維持する。
7. Issue URL・合意した仕様・現在ラベル・未解決事項を主エージェントに報告し、`demo-issue-specification`へ渡す。設計工程は自動開始しない。

## ラベル不足

`Spec`がない場合、スキル内で新設・編集しない。スキルのラベルなし作成がユーザーに承認された場合だけ、その契約内でIssueを作成できる。
作成済みならURLと現在値を報告し、「Spec設定未完了」として停止する。
ラベルの初期整備は別の明示依頼・承認で行う。状態未設定のIssueを設計開始可能とみなさない。

## 完了条件と証拠

- ユーザー確認済みの本文を持つIssueが存在し、本文・URLを再取得できる。
- 工程ラベルが`Spec`だけであることを確認できる。
- Issue URL、仕様合意、ラベル再取得結果、未解決事項、次工程を報告した。

スキルが複数Issueを作成した場合はIssueごとに証拠・未完了を区別する。
ローカルモードのMarkdownはGitHub Issueではないため、このフローの完了と扱わない。

## 停止・対象外

認証・権限・CLI不足、承認拒否、重要な仕様不足、結果不明では停止する。
結果不明時は読取で状態を確認し、作成を盲目的に再実行しない。
設計書作成、実装、worktree作成、commit・push・PR作成、ラベル定義の新設は行わない。
スキル終了後の操作をスキル実行中へ持ち込まず、禁止を別ツールで迂回しない。
