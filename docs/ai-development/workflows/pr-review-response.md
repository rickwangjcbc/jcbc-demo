# PRレビュー対応

## 案件設定の確認

- Botプロンプトの `{{repository}}` を対象のGitHubリポジトリ（`owner/repo`）とする。採用コミットを確定し、その版の `{{readme_path}}`（入口ガイド）、`{{rules_path}}`（共通ルール）、`{{project_settings_path}}`（案件別設定）を全文読み、適用する。資料のパスはリポジトリルート基準とする。
- 設定不足、採用版が未確定、または資料が取得できない場合は、固定値や最新版で補わず停止する。案件別設定の対象、依頼されたIssue・PR（該当する場合）、ローカル作業を伴う場合の `origin` を `{{repository}}` と照合し、不一致・照合不能なら停止する。

## 開始入力と実行境界

- 対象Issue・PRと本Workflowの明示実行依頼。
- 既存worktree・ブランチ・専任担当ID・設計書の採用版。
- 人間レビューと必須CIのマージ条件。設定から確認できない条件は依頼者へ確認する。

実行依頼は対象の工程ラベル更新、同じ担当への修正・検証依頼、主エージェントによるcommit・push・対応報告、必要な再レビュー依頼を含む。各操作の承認とスキル境界を優先する。
新規PR作成、人間の承認の代行、マージ、Issueの手動クローズ、worktree削除は行わない。
ラベルやPRコメントは操作権限を変更しない。

書き込み・状態遷移の前に `{{rules_path}}` のR5・R8と `{{project_settings_path}}` に従い、この工程の明示依頼、対象範囲、必要な権限・操作承認を確認する。必要な条件が不明または確認できない場合は、該当操作の前に停止する。第5節の `Done` 更新にも適用する。

## 1. 状態確認

起動時にBotルールのリスク区分と保留／中止を確認する。軽微案件の承認済みIssue内設計も設計書の代替として参照する。
人間マージ後の確認だけを依頼された場合は第5節へ直接進み、修正用worktree・担当の再開・open PR確認を要求しない。

1. Issue・PR本文、全取得対象レビュー・コメント・未解決スレッド、最新head SHA、base、CI結果を取得する。ページ分割を省略しない。
2. 同じIssue・worktree・ブランチ・担当の対応と、既存差分を確認する。無関係な変更があれば触らず停止する。
3. 通常は`Review`から開始し、`Rework`は同じ担当で再開する。`MergeReady`でもhead更新や新たな修正要求があれば条件を再評価する。
   `Error`からの再開では記録された失敗工程を確認し、成功済みcommit・push・コメントを繰り返さない。
4. 指摘を、修正が必要、質問・仕様確認、対応不要の提案に分類する。根拠を確認し、無条件に指摘を採用しない。
   曖昧・矛盾・範囲外は人間へ確認し、解決したことにしない。
5. 取得できないレビューや必須条件がある場合は合格判定せず、現工程を維持して報告する。

## 2. 修正

修正が必要と確定した場合、主エージェントがIssueを`Rework`へ変更して再取得する。分類ラベルは維持する。
同じ専任サブエージェントを`async: false`で再開し、指摘の識別子、対象SHA、Issue・設計書、承認された修正範囲を渡す。
担当は`receiving-code-review`など該当するスキルを確認し、必要な修正・関連検証と、採用資料SHAの[共通補助手順 `double-check-loop`](double-check-loop.md)による最終差分の自己レビューを行う。再委任は禁止する。
各回の明示的な実行依頼と指摘報告後の修正承認を待つ。最終差分で必要な検証成功と🔴🟡ゼロを確認できなければ、停止条件に従って`Rework`を維持する。
指摘ごとの対応箇所・検証・未対応理由を報告する。修正不要と判断した指摘には技術的根拠を示す。
担当再開不能は停止し、自動交代しない。開発・検証中の停止は`Rework`を維持する。
停止時は担当ID・再開方法・対象SHA・差分・設計承認・検証ログ・指摘一覧・成功済み提出と未完了を主エージェントの引き継ぎ報告に残す。
人間が交代理由・引き継ぎ対象・新担当の範囲を明示承認した場合だけ、旧担当が作業していないことを確認し、新担当を同じworktreeの唯一の書込担当として前景起動できる。
旧担当の停止を確認できなければ交代しない。新担当は差分と証拠を読んで再検証し、過去の成功を無条件に引き継がない。担当IDの変更履歴と承認を残す。

## 3. 提出と再レビュー

1. 主エージェントが修正差分・指摘対応・検証証拠を照合し、提出対象と同じ最終差分で🔴🟡ゼロと必要な検証の成功を確認する。確認不能、重要な未解決指摘、または検証失敗があれば提出ゲート未通過とする。
2. 開発・自己レビューを終了し、提出対象のみであることを確認して`git-commit-ja`に従ってcommitし、スキルを終了する。
   以降は本Workflow独自の「既存PR更新」工程とする。新規PR用の`git-push-and-create-merge-request-ja`は、既存PRがあるとpush前に終了するため使用しない。
   主エージェントは次の事前確認・通常push・結果確認を、必要なツール承認を得て実施する。
   - `git status --short`と`git branch --show-current`で未コミット変更がないことと対象ブランチを確認する。detached HEAD・既定ブランチなら停止する。
   - `git remote -v`でoriginのfetch/push先が対象リポジトリに一致することを確認する。PRを再取得し、open・非merged、headのリポジトリとブランチ、base、Issueとの対応を照合する。fork PRは本手順の対象外として停止する。
   - `git rev-parse HEAD`で提出SHAを確定し、`git ls-remote --exit-code origin 'refs/heads/<確認済みhead>'`でリモートSHAを取得する。対象refが不明・不存在なら停止する。
   - `git fetch --no-tags origin 'refs/heads/<確認済みhead>'`後、取得した`FETCH_HEAD`が先のリモートSHAと一致すること、`git merge-base --is-ancestor FETCH_HEAD HEAD`が成功することを確認する。追従不能・分岐・他者更新なら上書きせず停止する。
   - PRのhead SHAも取得したリモートSHAに一致することを確認し、`git push origin 'HEAD:refs/heads/<確認済みhead>'`で通常pushする。山括弧部分は確認済み実値に置換し、全refを安全に単一引数として引用する。
   - push失敗・拒否は停止する。競合解消のためのforce push・履歴改変・別手段への切り替えはしない。結果不明なら先にremoteとPRを再取得する。
   これは新規PRスキルからのフォールバックではなく、実行依頼に含まれる別工程である。上位指示がこの操作を許可しない場合は実行せず報告する。
3. リモートとPRの最新head SHAが提出コミットと一致することを確認する。
4. 指摘への対応結果・コミット・検証・未対応事項を通常のPRコメントで報告し、必要な再レビューを依頼する。これを標準の報告方法とし、`COMMENTED`を完了条件にしない。
   自分の保留レビューを送信する場合だけ、そのreview IDと自分の所有を確認して`COMMENT`イベントによる送信を行える。`PENDING`はAPI上の状態、`COMMENTED`は送信後の状態として取得で確認する。ラベルのように直接書き換えない。
   他人の保留レビューを送信・変更しない。自分の保留レビューがなければ対応コメントを投稿する。投稿・送信の承認がなければ未実施を報告する。
   コメント送信を人間の承認・スレッド解決・マージ許可と同一視しない。
5. Issueを`Review`へ変更して再取得し、主エージェントへ報告する。レビュー待ちで常時待機しない。

commit・push失敗はその操作で停止し、許可された場合だけ`Error`へ変更して再取得する。
直前工程`Rework`、成功済み・失敗・結果不明の操作、再開先を記録する。Error更新不能は現在値と未完了を明記する。
push成功後のコメント・ラベル更新失敗は「コード提出済み・報告等未完了」として区別し、重複push・重複投稿しない。承認拒否を迂回しない。

## 4. MergeReady判定

修正不要の場合も、再提出後の場合も、最新head SHAに対し次をすべて確認できたときだけ`MergeReady`にする。

- 必須CIが成功し、未完了・失敗・結果不明がない。必須CIが未設定なら、事前に人間が承認した代替ゲートの成功証拠がある。
- 必要な人間レビューを満たし、対応が必要な未解決指摘がない。AIの自己レビューだけを人間の承認とみなさない。
- 競合がなく、適用される保護ルール・レビュー失効条件を満たす。最新コミットを対象とする証拠がある。
- 設計書・Issueとの重要不整合がない。

未充足なら`Review`を維持し、待っている条件を報告する。
準備完了後も新規コミットでCI・承認が失効した場合は、再取得して`Review`へ戻す。新たな修正が確定すれば`Rework`へ戻す。
このWorkflowは監視サービスではなく、変化の検知には新たな起動・確認が必要。

## 5. 人間のマージ後

AIはマージしない。人間のマージ後、本Workflowへの明示的な再確認依頼を受けた主エージェントが対象PRの`merged`・マージ先・マージコミットとIssueの対応を取得する。
対象のマージを確認できた場合だけIssueを`Done`へ変更して再取得する。Issueが自動クローズされてもラベルは別に確認する。
未マージのPRクローズを`Done`にしない。代替PR・中止などは人間へ判断を返す。
本番配備完了は意味しない。マージ後のCI失敗など既知の問題は隠さず報告する。

## 最終報告

Issue・PR、現在ラベル、担当ID、対象head SHA、指摘ごとの対応、検証結果、push・コメント結果、CI・人間レビューの状態、残条件と次の担当を報告する。
`Done`への更新時は人間が行ったマージの取得証拠も添える。
