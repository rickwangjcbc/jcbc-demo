# 開発・検証・PR提出

## 案件設定の確認

- Botプロンプトの `{{repository}}` を対象のGitHubリポジトリ（`owner/repo`）とする。採用コミットを確定し、その版の `{{readme_path}}`（入口ガイド）、`{{rules_path}}`（共通ルール）、`{{project_settings_path}}`（案件別設定）を全文読み、適用する。資料のパスはリポジトリルート基準とする。
- 設定不足、採用版が未確定、または資料が取得できない場合は、固定値や最新版で補わず停止する。案件別設定の対象、依頼されたIssue・PR（該当する場合）、ローカル作業を伴う場合の `origin` を `{{repository}}` と照合し、不一致・照合不能なら停止する。

## 開始入力と実行境界

- 対象Issueと本Workflowの明示的な実行依頼。
- 設計で使用した同じIssue専用worktreeの絶対パスと作業ブランチ。このworktreeを実装・ローカル検証・AIレビューに共通して使う。
- リスク区分と承認済み設計資料の参照先・承認記録。軽微案件は人間が承認したIssue内簡易設計で代替できる。その他の設計書なしの例外も理由と人間の承認が必要。
- マージ先（指定があれば）。

本Workflowの実行依頼は、対象Issueの工程ラベル更新、採用方式に従う担当への委任、提出ゲート通過後のcommit・push・PR作成を含む。
閲覧・編集は実行依頼ではない。上位指示・スキル境界・ツール承認を優先し、ラベルや設計資料を実行許可とみなさない。
主エージェントは工程管理・提出を担当し、実装を兼ねない。各担当は採用方式で割り当てられた工程だけを行い、再委任しない。

## 1. 開始前確認

書き込み・状態遷移の前に `{{rules_path}}` のR5・R8と `{{project_settings_path}}` に従い、この工程の明示依頼、対象範囲、必要な権限・操作承認を確認する。必要な条件が不明または確認できない場合は、該当操作の前に停止する。保留／中止を確認し、高リスク案件では案件別の追加ゲート・専門レビュー条件を開始前に確認する。
以降の「設計書」は、承認された軽微経路ではIssue内簡易設計と読み替え、存在しないファイルパスを要求・生成しない。

1. Issue本文・全対象コメント・受け入れ条件・対象外を確認する。通常開始は`Todo`のみとする。
   `Imp`からの再開は採用方式に従い、担当または引き継ぎ記録と過去の証拠を確認する。`Error`は後述の再開条件に従う。`Review`以降はレビュー対応Workflowへ渡し、PRを重複作成しない。
2. 実行依頼・Issue本文・コメントから設計書を特定する。指定がなければ対象worktreeの`specs/`を確認する。
   候補が複数、対応不明、指定ファイル欠落、設計承認不明、重要仕様の矛盾があれば停止する。更新日時だけで選ばない。
   設計書がない場合は勝手に進めず、設計なしの例外承認または設計工程への差し戻しを依頼者へ確認する。
3. Issue・worktree・ブランチの対応、既定ブランチでないこと、既存担当を確認する。専任担当の実作業先と検証コマンドの実行先が、指定された同じworktreeであることを確認する。一致を確認できなければ、実装・検証を開始しない。AIはworktreeを作らない。
4. 既存差分を確認する。無関係な変更があれば戻す・退避する・取り込むことなく停止する。
   開始前からある設計書も記録し、承認済み資料か、変更・提出してよいかを確認する。関連資料という理由だけで自動的に変更・コミットしない。
5. Issueと設計書の確定仕様を検証方法へ対応付ける。コマンドは作業対象のルート `README.md` と設定から決める。入口ガイド `{{readme_path}}` とは区別する。
6. `Imp` に変更する前に、R2と案件別設定に従い、必要な権限と継続方式を確認する。標準方式は同じ担当の前景再開の実績を、同一対話セッション方式は実地検証記録と適用範囲を含む人間の採用承認を確認する。工程別引き継ぎは、開発依頼で人間が対象Issue・採用ルールのコミット・方式を明示した場合だけ選ぶ。承認済み設計・専用worktree・操作権限を照合し、実際に使うBot・スキル・ツールの制約が、新規前景起動・読み取り専用レビュー・承認後の別修正と両立することを確認する。模擬Issue・検証専用worktree・過去の実地検証ログ・別個の方式採用手続きは要求しない。方式や必要な条件を確認できない、または両立しない場合はラベルを変えず停止し、別方式から自動で切り替えない。

## 2. Impと専任担当

`Imp` からの再開時は、実装・ローカル検証の結果と対象差分を照合し、完了済みの作業を繰り返さない。レビュー待ちなら書込担当を起動せず、第4節のレビューの明示依頼を待つ。依頼があれば採用方式でレビューだけを行う。修正承認待ちの場合も、第4節の条件を満たすまで書込担当を起動しない。以下の実装担当の起動手順は初回または未完了の実装・検証に限る。

主エージェントが`Imp`へ変更し、他の工程ラベルを外して再取得する。分類ラベルは維持する。
再取得後、対象worktreeで事前確認済みの方式を使う。標準方式では専任担当1名を `async: false` で起動し、既存担当がいる場合は同じ担当を前景再開する。同一対話セッション方式では、担当を待機させ、次の作業の明示依頼・承認が届いてからだけ送信する。
工程別引き継ぎを採用済みの場合は、実装担当を `async: false` で1件起動し、実装・テストの差分と結果を返して終了させる。明示依頼を受けた各工程に限り、R2の記録と実状態を照合して、新しい前景セッションを1件ずつ起動する。前の書込担当の終了・対象差分が確認できない場合は起動しない。
再開・引き継ぎ前に担当・セッション・Issue・worktree・ブランチ・対象差分（基準SHA、HEAD、未コミット差分と未追跡の提出対象）・成功済み／未完了操作を照合する。不一致や再開不能なら停止し、自動で切り替えない。
R2の引き継ぎ記録に加え、再開記録には方式・担当ID・セッション識別情報・確認済み再開方法・Issueと設計承認・worktreeとブランチ・対象差分・検証ログ・レビュー回数・提出済み操作・未完了を含め、次の主エージェントが参照できる場所を報告する。
人間が交代理由・対象・範囲を明示承認した場合だけ、旧担当の停止を確認して新担当を唯一の書込担当として起動する。停止を確認できなければ交代しない。
新担当は証拠と実差分を照合し、必要な検証を再実行する。交代承認・新旧IDを記録し、レビュー回数や不合格を交代でリセットしない。

依頼には次を含める。

- Issue、設計書のパス・採用版・承認状態、確定した追加仕様。
- 実装前に両方を読み、矛盾・重要な不足があれば主エージェントへ返すこと。
- 設計書自体の変更・提出可否、既存差分の範囲。
- 同じ担当が実装・必要な検証を行い、結果と対象差分を返して制御を戻すこと。`double-check-loop` は各回の明示依頼を受けるまで開始しないこと。
- 再委任、commit・push・外部更新を担当が行わないこと。提出は主エージェントが行う。

主エージェントが読んだだけで担当も読んだとはみなさず、報告で参照資料を確認する。
起動失敗は`Imp`のまま未着手と報告し、別担当や別CLIへ自動切り替えしない。

## 3. 開発・テスト

担当はIssueの範囲だけを実装し、設計書の確定仕様と照合する。推奨例や対象外の記載を追加実装の許可として扱わない。
重要な設計変更・仕様矛盾・対象外変更・権限不足は主エージェントへ返す。
変更前後の検証を分け、単体・E2E・lint・型チェック・ビルドなど必要なローカル検証を、実装と同じIssue専用worktreeで行う。最終検証はそのworktreeの提出対象と同じ差分に対して実行し、別worktreeでの結果を代用しない。
環境不足・不合格・未実行を区別する。テスト削除・無効化・期待値の弱体化はしない。
文書のみなど非該当の検証は理由と代替確認を示す。停止時は`Imp`を維持する。

## 4. double-check-loop

採用資料SHAの[共通補助手順 `double-check-loop`](double-check-loop.md)に従い、未追跡の提出対象も含む最終差分を確認する。同じ担当の方式は自己レビュー、工程別引き継ぎは新規前景セッションでの読み取り専用レビューとし、修正は別途承認後の別セッションで行う。
各回の明示的な実行依頼と指摘報告後の修正承認を待つ。再確認枠や承認が不足する場合、または必要な検証・最終差分の🔴🟡ゼロを確認できない場合は提出せず、停止条件に従って`Imp`を維持する。

## 5. PR提出ゲート

主エージェントが担当報告・実差分・検証記録を照合する。採用方式で定めるレビュー以外に、追加レビュー担当は起動しない。

- Issueの各受け入れ条件と設計書の確定仕様に実装・検証証拠がある。
- 最終差分に必要な検証が成功し、同じ最終差分のAIレビューで🔴🟡がゼロ。
- 重要な設計不整合・権限問題・無関係な変更がない。
- 合意した設計変更があれば、必要なIssue・設計書更新が許可された工程で完了している。

未達なら`Imp`のまま停止する。ここでは`Done`へ変更しない。

## 6. commit → push → PR → Review

開発・AIレビュー工程を終了した後、主エージェントが提出操作へ切り替える。

1. 全変更が対象Issueの提出対象であることを確認する。設計書も提出許可済みのものだけを含める。
   提出対象外の未コミット資料が残り、全変更を対象にするスキルと両立しない場合は停止する。勝手に削除・退避しない。
2. `git-commit-ja`の定義に従ってcommitし、コミットIDと残存差分を確認する。
3. 新規PRに限り`git-push-and-create-merge-request-ja`の定義に従い、対象Issue・マージ先を明示してpushし、成功確認後にPRを作成する。
   既存PRが見つかると同スキルはpush前に終了する。スキルを終了して状態を報告し、既存PRの更新は`pr-review-response`への明示依頼で行う。重複作成や無断の手段変更はしない。
4. PR本文に`Closes #対象番号`、設計書の参照、検証結果・未検証範囲・主要な設計変更を記載する。
   GitHub上でローカル絶対パスを使わず、提出済みのパス・URLを使う。未公開ならその旨を記し、存在しないリンクを作らない。
5. PRの存在、対象Issue・head/base・最新コミットの対応を再取得で確認する。CI未完了を成功と表現しない。
6. Issueを`Review`へ変更して再取得し、主エージェントへ報告する。ラベル更新できなければ「PR作成済み・Review更新未完了」と現在値を報告し、重複提出しない。

## 7. Errorと再開

commit・push・PR作成の失敗、承認拒否、実行阻害はその操作で停止する。
許可される場合だけ`Error`へ変更して再取得する。ラベル操作も拒否・禁止なら試みない。
更新できなければ現在値と「Error更新未完了」を報告する。
直前工程、成功済み操作、失敗・結果不明の操作、コミット・PR、再開先を記録する。
結果不明時はローカルcommit・リモート・既存PRを確認し、成功済み操作を再実行しない。拒否を別手段で迂回しない。

再開は対象と本Workflowへの明示依頼を受け、同じIssue・worktreeで、採用済みの方式に従って行う。
提出だけなら成功済み操作を再利用して未完了だけ再開する。コード変更が必要なら`Imp`へ戻し、検証・AIレビューを再実施する。
PR提出を確認できたら`Review`へ進める。担当再開不能なら自動交代せず依頼者へ返す。

## 8. 最終報告と終了条件

- Issue、工程ラベル、worktree、ブランチ、担当ID。
- 設計書の採用版・参照パス・提出状態、受け入れ条件への対応。
- 検証を実行したworktree・対象差分、検証コマンドと結果、未実行・環境不足、AIレビュー各回と最終差分。
- コミットID、push結果、PR URL、CIとレビューの取得時点の状態。
- 成功済み・未完了・次の担当と作業。

正常終了はPRの存在・最新コミットと`Review`を確認して報告した状態。レビューの返答を待ち続けず終了する。
指摘対応は`pr-review-response`へ渡す。マージ、Issueの手動クローズ、worktree削除は行わない。

## 操作境界

スキル実行中に別工程のラベル更新等を持ち込まない。既存スキルの禁止をWorkflowで解除しない。
本定義はラベルの監視・自動起動、必須CI・保護ブランチを実装しない。実環境での権限と全工程の動作は別途確認する。
